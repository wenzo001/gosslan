## 复跑


每条新增判据都跑过"改坏即 FAIL、恢复即 PASS"：摘掉 `state.rs` 的接线、把 `.ok();` 装回去、
把 `done` 那道旧闸门装回去、把计数改成"拿不到也计一笔"、把错误文本的截断改成原样返回，
各自都让对应那条报红（详见提交说明）。

## 覆盖边界（别读成"已经覆盖全仓"）

- 持锁观测只覆盖经 `DbLock` 的取锁；`try_lock` 拿不到的那次不计；**测不出是谁拿的**（没有标签体系）。
  `check-lock-scope` 那条"锁内不许 emit"的守卫仍只管 emit，本批没有扩它。
- 上一轮记录只读当前 `.log` 尾部，轮转掉的 `.old.log` 不读；进环后按内存环上界淘汰，永久的那份在盘上。
- `progress-touch` 与 `incomplete-record` 两格只在真实 `AppState` 路径上跑，单测只能钉到"调用点存在"这一层。
- note 里那句是 **SQLite 自己的错误文本**，只加了字符上界，不是"已证明不含路径"：rusqlite 里唯一自带路径的
  变体是 `InvalidPath`（只在打开库文件时产生，非 unix 平台），收尾这条路上碰不到；上界是给未知形状留的。

## 仍要真机验的

1. 传大文件到一半杀发送端：接收台账是否还会长时间停在 active（现在会留下一行 stage 痕）。
2. macOS 界面冻住时抓一次线程栈，与 `db 持锁观测` 那行的"最长持有/最长等待"对时点。
3. Windows 长跑 ≥12 h 的工作集曲线（本批只减了"无痕"，没动内存）。
4. 打开 15 MiB 图片时的 WebView 长任务（`number[]` 那条回传路径本批未动）。
5. Android 发布版启动异常能否从 logcat 取到 `channel=panic`。
