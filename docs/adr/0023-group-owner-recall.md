# ADR-0023: 群主/管理员特权撤回共用同一条 recall 帧；新版本支持有界重放，老版本如实提示

- Status: **Accepted**（2026-10-28；2026-11-27 修订为群主/管理员 + 有界重放）
- Date: 2026-10-28（2026-11-27 修订）
- Owners: Gosslan
- 相关：ADR-0011（Gossip 信封认证 —— 本 ADR 的"谁发的不可伪造"全靠它）、
  ADR-0007 / INV-P24（跨版本兼容与优雅降级；线格式仍零改动，但新增本地有界重放表）、
  INV-P26（落盘证据态：撤回不改台账语义）、`CONTEXT.md`（群主 / 可撤行 / 离链≠删本体 的术语）
- 它推翻的旧口径：`commands/group_announcements.rs` 原先写着「权限：仅原作者。不做"群主撤他人"
  —— 那需要引入管理员角色」，`protocol::recall_verdict` 的注释与之同口径。

---

## 1. 需求落在系统里的形状

这个应用**没有中心服务器**，也就没有"服务端替群主执行"这条路。所以"管理者特权"必须翻译成
每条设备上都能自己判的一句话。现成的锚点是 `groups.creator` 与 `groups.admins`：任一本地
管理者身份匹配发帧人即获管理档授权；转让仍只改 `creator`，管理员任免只由群主权威下发。

需求里的三句口语各自要钉一个边界，否则会变成实现者自己猜：

| 原话 | 钉住的口径 |
|---|---|
| 「任何人的任何消息」 | 取消「必须是作者」；**不**取消类型分母（分母为什么不能加卡片见 §3.6） |
| 「不限制时间」 | 群主档不查窗口。接收端本来就不查时钟（既有口径：那是产品规则不是安全边界），所以这一条在老版本上也早已成立 |
| 「让群聊天列表里消失…任务在任务列表里还是可以看到」 | 撤回只作用于**消息行**（离链）；当前任务/公告仍与消息同真源，撤卡会删本体，因此不在可撤分母内；群文件有独立台账，正文撤回不删文件台账 |

## 2. 决策

| 决策点 | 取定的形状 | 为什么是它 |
|---|---|---|
| 授权怎么表达 | `recall_verdict` 多一个入参 `RecallAuthority{Author, GroupCreator}`，**同一个函数**两档分支 | 分成两个函数迟早漂；分档只改"看哪些条件"，不改落地路径 |
| 接收侧怎么判 | 另有一份纯函数 `recall_receive_allowed`，比较的是**本机库里**的 creator/admins 与成员表 | 它问的不是"这条命令合不合法"，而是"我凭什么信发帧人"。发帧人自报角色不作数；`sender_id` 被 Ed25519 签名锁住，转让/任免各有权威闸 |
| 可撤的分母 | **两档共用同一份**（`text / code / image / file / merge`） | 卡片看着最像「能撤」，但它没有独立真源 —— 撤卡就是删本体，见 §3.6。判据在 `CONTEXT.md::可撤行` |
| 校验落在哪一层 | 前端只决定入口显不显示；发送端命令层现读 `groups.creator/admins` 选档；**接收端再独立判一次** | 三层各自成立，任何一层被改掉都不会把越权变成可能。反面先例是本仓已有的 `pin_group_message`（自称"任意群成员"却没在命令层校验，只靠内核兜） |
| 协议形状 | **线格式零改动**：还是那条 `kind="recall"` + `{"target":…}`；新增本地 `pending_group_recalls` 表 | 签名意图在接收侧隔离，权限追上后重放；不改老端线格式 |
| 跨会话 | 接收侧新增「目标消息的 conv_id 必须等于信封的 conv_id」这条闸，**与特权同批** | 作者档时代这个洞只泄露自己的内容；有了群主档，A 群群主可以拿一条 A 群的合法信封去清 B 群里别人的消息 |
| 在途附件 | 收到撤回帧的设备**各自**停本机那一笔，且用 `CancelNotify::LocalOnly` 不再外发 | 那条 recall 帧本来就全群广播过；每台都再发一份 `FileCancel` 就成一个撤回引发 N 份取消通知（回声）。真正的发送方自己也会收到那条帧，由它停自己的发 |
| 撤回后的残留 | 物化后复用删除那一份 `refresh_conversation_summary`（会话预览 + 未读一起收敛） | `messages.content` 清空对搜索/导出/已读水位自动正确，但会话列表读的是 `conversations.last_msg`（**存储列**）。`db/recalls.rs` 原先写着"会话预览一行都不用改"，那句话与实现相反 |
| 界面怎么说 | 提示行按撤回者分两式（自撤＝「消息已撤回」，他人撤＝「群主/管理员撤回了这条消息」），**不额外发通知**；跨人撤回的确认弹窗带作者与原文摘要，并说明新版本重放、老版本可能不生效 | 撤回者身份本来就存在事件行的 `sender_id`（墓碑表也有 `recaller_id`），不需要新字段。批量整理刷屏时给每人弹一条横幅是噪音 |
| 版本不一致怎么处置 | 新增能力位 `CONTENT_FEATURE_CREATOR_RECALL`，**只用来算那句提示**（unsupported / unknown 两态照 `kind_audience` 的既有口径分开），不门控 | 见 §3 第 2 条 |

## 3. 为什么不（被否掉的四个形状）

1. **加一个新 kind（如 `recall_by_owner`）或给载荷加 `by_creator` 字段。** 加 kind 就是把
   「不扩散协议消息类型」这条既有口径再破一次；而且老端**照样不认**，同步问题一点没解决，
   只是多欠一笔协议债。加字段同理：老端反序列化会忽略未知字段，但它的接收侧判据仍是"只认作者"，
   字段发过去也不改变它的决定。差别只在接收侧**那半代码**，所以改那半就够了。
2. **能力位硬门：全群成员都确认支持才允许群主按。** 看着最"实"，但它会把功能按住：
   对端能力位只存在内存里（`peer_content_features`，重启即空），而群成员**离线是常态** ⇒
   大多数成员是 unknown。本仓已经明确反对把"不知道"算成"不支持"（`kind_audience` 的注释
   就是那次记账）：那样要么永远给按不了，要么提示永远在响。所以这一位只用于**如实说明**。
3. **静默事件行也开撤回。** 它们不在时间线上，"撤"它们不是离链而是**回滚那个动作**
   （撤 pin＝取消置顶？撤 reaction＝删表情？），而 `todo_update` 是 LWW 状态改动，撤回
   既不能让它倒退也没有东西可看 —— 要做得另立一套"群主否决"的语义，比本功能本身更大。
4. **系统提示行也开撤回。** 实测形状：`commands::insert_system_message` 里
   `msg_id = sys-<uuid4>` **每台设备各自生成、不广播**。拿它发撤回只有发起者自己那台会消失，
   界面却写着"已撤回" —— 那是把假同步做进产品。
5. **顺手把收藏 / 系统通知 / @提醒一起改。** 撤回后这些残留是**已知缺口**（本次一并记档），
   但都不是"屏幕上还挂着已撤内容"这一条链：收藏是收藏者自己的快照与媒体副本（`favorites.content`
   / `media_path`），群主权限越进去就是动别人的数据。捆在一起做会把一批改动铺到 5 个领域上，
   回归面与这一批完全不成比例。

### 3.6 一条被 review 抓到的假事实：「撤卡片只是离链，本体照旧可见」

本节的存在是因为我把这句话写进了 §1 与 §2，并据此给群主档加过 `announcement / todo / poll`
三种卡 —— **那句话是错的**。证据（全部现读）：

- 任务看板取数：`messages WHERE conv_id = ?1 AND kind IN ('todo','todo_update')`
  （`src-tauri/src/db/messages.rs:145`）；
- 公告栏取数：`messages WHERE kind IN ('announcement','announcement_delete')`
  （`src-tauri/src/commands/group_announcements.rs:32`）；
- 卡片级唯一有独立表的是群文件（`db.rs` 的 `group_files`）；`group_todos` / 公告表
  现算 `grep -c 'CREATE TABLE.*group_todo' src-tauri/src/db.rs` = 0。

所以撤一张卡 = 那行 `kind→recalled` + `content→''` = **本体一起从看板/公告栏消失**，
而墓碑是 G-Set（只增不减）⇒ 不可恢复。这与负责人原话「任务的话 其实在任务列表里还是
可以看到它」正相反，因此三张卡**从分母里撤回**，两档共用 `RECALLABLE_KINDS`。

要真支持「卡片离链但本体留着」，前置条件是先做一次真源搬家（看板与公告栏各自建表，
消息行退成「展示出来的那一张卡」）—— 那是比本功能更大的一件独立事。做完之后把三张卡
放回分母，并同步 `CONTEXT.md::可撤行`、`protocol.rs` 与 `src/utils/recall.test.ts`
里那条「不许再有第二份清单」的判据（它同时钉着「那两张表还不存在」，所以搬家一旦发生
这条判据会主动提醒来改）。

## 4. 它挡不住什么（诚实边界）

- **挡不住群主/管理员滥用**：没有申诉、没有远程审计、没有冷却。唯一的追溯路径是**每台设备本地**那份
  墓碑（`group_recalled_messages` 存 `recaller_id` + `seq`）。这是无服务器架构下的固有上限。
- **新版本最终一致有边界**：转让/任免导致接收时权限不足的签名 recall 会进入 `pending_group_recalls`，
  在启动、群快照提交、转让/任免和目标消息到货时重放；生效前重新核对当前管理者与成员身份。
  全局 256 条、每群 64 条、每发送者 32 条、信封 256 KiB、TTL 7 天，超限按最旧淘汰，失败重放指数退避。
  这是“有界最终一致”，不是无限期保证；容量满、TTL 到期或设备永不上线仍可能不收敛。
- **老版本没有重放能力**：老端仍按旧规则拒绝，发送端能力提示只解释结果；新版本不能替老端补做重放。
- **签名意图隔离不等于发送时授权证明**：普通成员的非法/未来可能合法的 recall 也会先入隔离队列，
  但只有当前管理者身份复核通过才生效；若要求“只有发送时已获授权的意图才能入队”，必须另引权威证明/epoch，
  属于后续协议演进，不在本轮范围。
- **先撤后到这条通道必须「命中后再复核」**（2026-10-28 第二轮 review 抓到的严重）：墓碑可能在
  还不知道作者/类型/会话时就被收下（那一刻只有「发帧人是本群成员」可判），而墓碑表按 `msg_id`
  建索引、PK 却是 `(conv_id, msg_id)` ⇒ 单看命中会误伤别的会话的同名消息。现在到货那一臂会用
  拿到手的事实（作者、类型、会话、撤回者在本机记录里是不是群主/管理员）**重判一遍**，不过就按原文落库
  并留 `code=RECALL_TOMBSTONE_NOT_APPLIED`。不复核的后果写在这里：普通成员抢在目标落库前
  广播一条 recall，就能毁掉分母之外的卡片、或另一个会话的消息，而界面那句「群主撤回了这条消息」
  跟着说错话。
- **管理者角色按设备**：creator 与 admins 都是 device_id；同一个人的其它设备不会自动继承角色。
  转让只改 creator，管理员名单随群主 GroupKey 权威下发。
- **「再也找不回」只对行内正文成立**：`text / code / merge` 撤了确实不可恢复；但 `image / file`
  已传完的副本仍在磁盘、群文件台账（`group_files` 表）也没有随撤回删除点，收藏快照同理（§3.5）。
  撤回的作用域是**聊天时间线**，不是「把所有副本销毁」。
- **不可逆**：墓碑是 G-Set（`INSERT OR IGNORE`，只增不减），所以**没有"撤回的撤回"**；
  要做只能另立"隐藏/恢复"两套语义，那是比本功能更大的一件事。
- **已知未修的残留**（记档，不在本 ADR 的承诺范围内）：会话预览本 ADR 修了；
  收藏快照与媒体副本、系统通知不撑销、@提醒指向、已撤回卡片在收藏里的呈现 —— 都还在。

## 5. 验证边界

2026-11-27 修订后的本地判据：

- `db::pending_recall_tests::*`：权限追上后重放、先撤后到、TTL/信封上限、容量淘汰；
- `tests::pending_recall_replay_is_wired_to_rejection_transfer_target_and_startup`：拒绝入队、目标到货、
  转让与启动四条接线；
- `protocol_tests` / `src/utils/recall.test.ts`：授权矩阵、可撤分母、跨会话与界面契约；
- 完整 Rust 库测试与前端测试结果以本轮实际命令输出为准，不在 ADR 里手抄条数。

未验（不许当成已过）：真实双设备转让竞态、老版本实际拒绝、重启/崩溃后的跨进程重放、
容量压力与 7 天 TTL 真机等待。老版本最终一致不在承诺内。
