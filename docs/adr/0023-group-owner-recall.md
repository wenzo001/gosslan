# ADR-0023: 群主特权撤回用的是**同一条 recall 帧换一档授权**；每台设备各自裁决，老版本如实提示

- Status: **Accepted**（2026-10-28，负责人拍板：「群里群主可以随意撤回任何人的任何消息，
  不限制时间，和各种限制，任意一条，这是个特权功能，做好安全校验和同步体验」）
- Date: 2026-10-28
- Owners: Gosslan
- 相关：ADR-0011（Gossip 信封认证 —— 本 ADR 的"谁发的不可伪造"全靠它）、
  ADR-0007 / INV-P24（跨版本兼容与优雅降级 —— 本 ADR 明确选了"零协议改动 + 只提示"那一档）、
  INV-P26（落盘证据态：撤回不改台账语义）、`CONTEXT.md`（群主 / 可撤行 / 离链≠删本体 的术语）
- 它推翻的旧口径：`commands/group_announcements.rs` 原先写着「权限：仅原作者。不做"群主撤他人"
  —— 那需要引入管理员角色」，`protocol::recall_verdict` 的注释与之同口径。

---

## 1. 需求落在系统里的形状

这个应用**没有中心服务器**，也就没有"服务端替群主执行"这条路。所以"群主特权"必须翻译成
每条设备上都能自己判的一句话。现成的锚点只有一个：`groups.creator`（单列、可转让、
成员表里**没有角色列**）。于是特权 = 「本机库里那条 creator 等于发帧人」，而不是任何新的权限体系。

需求里的三句口语各自要钉一个边界，否则会变成实现者自己猜：

| 原话 | 钉住的口径 |
|---|---|
| 「任何人的任何消息」 | 取消"必须是作者"；**不**取消类型分母（见 §2 第三行） |
| 「不限制时间」 | 群主档不查窗口。接收端本来就不查时钟（既有口径：那是产品规则不是安全边界），所以这一条在老版本上也早已成立 |
| 「让群聊天列表里消失…任务在任务列表里还是可以看到」 | 撤回只作用于**消息行**（离链）；卡片背后的本体（看板 / 公告栏 / 文件台账）是各自独立的真源，照旧可见。这不是遗漏，是撤回的语义边界 |

## 2. 决策

| 决策点 | 取定的形状 | 为什么是它 |
|---|---|---|
| 授权怎么表达 | `recall_verdict` 多一个入参 `RecallAuthority{Author, GroupCreator}`，**同一个函数**两档分支 | 分成两个函数迟早漂；分档只改"看哪些条件"，不改落地路径 |
| 接收侧怎么判 | 另有一份纯函数 `recall_receive_allowed`，比较的是**本机库里**那份 `groups.creator` | 它问的不是"这条命令合不合法"，而是"我凭什么信发帧人"。发帧人自报群主不作数；`sender_id` 被 Ed25519 签名锁住（ADR-0011），转让又有 `g.creator == from` 的闸 ⇒ 成员既不能自封群主，也不能把普通撤回伪装成群主撤回 |
| 可撤的分母 | 作者档不变（5 种用户内容）；群主档 = 那 5 种 + `announcement / todo / poll` 三张卡 | 只有**跨设备同源**的行撤了才等于"全群都消失"。判据在 `CONTEXT.md::可撤行` |
| 校验落在哪一层 | 前端只决定入口显不显示；发送端命令层现读 `groups.creator` 选档；**接收端再独立判一次** | 三层各自成立，任何一层被改掉都不会把越权变成可能。反面先例是本仓已有的 `pin_group_message`（自称"任意群成员"却没在命令层校验，只靠内核兜） |
| 协议形状 | **零改动**：还是那条 `kind="recall"` + `{"target":…}` | 见 §3 第 1、2 条 |
| 跨会话 | 接收侧新增「目标消息的 conv_id 必须等于信封的 conv_id」这条闸，**与特权同批** | 作者档时代这个洞只泄露自己的内容；有了群主档，A 群群主可以拿一条 A 群的合法信封去清 B 群里别人的消息 |
| 在途附件 | 收到撤回帧的设备**各自**停本机那一笔，且用 `CancelNotify::LocalOnly` 不再外发 | 那条 recall 帧本来就全群广播过；每台都再发一份 `FileCancel` 就成一个撤回引发 N 份取消通知（回声）。真正的发送方自己也会收到那条帧，由它停自己的发 |
| 撤回后的残留 | 物化后复用删除那一份 `refresh_conversation_summary`（会话预览 + 未读一起收敛） | `messages.content` 清空对搜索/导出/已读水位自动正确，但会话列表读的是 `conversations.last_msg`（**存储列**）。`db/recalls.rs` 原先写着"会话预览一行都不用改"，那句话与实现相反 |
| 界面怎么说 | 提示行按撤回者分两式（自撤＝「消息已撤回」，他人撤＝「群主撤回了这条消息」），**不额外发通知**；跨人撤回的确认弹窗带作者与原文摘要 | 撤回者身份本来就存在事件行的 `sender_id`（墓碑表也有 `recaller_id`），不需要新字段。批量整理刷屏时给每人弹一条横幅是噪音 |
| 版本不一致怎么处置 | 新增能力位 `CONTENT_FEATURE_CREATOR_RECALL`，**只用来算那句提示**（unsupported / unknown 两态照 `kind_audience` 的既有口径分开），不门控 | 见 §3 第 2 条 |

## 3. 为什么不（被否掉的四个形状）

1. **加一个新 kind（如 `recall_by_owner`）或给载荷加 `by_creator` 字段。** 加 kind 就是把
   「不扩散协议消息类型」这条既有口径再破一次；而且老端**照样不认**，同步问题一点没解决，
   只是多欠一笔协议债。加字段同理：老端反序列化会忽略未知字段，但它的接收侧判据仍是"只认作者"，
   字段发过去也不改变它的决定。差别只在接收侧**那半代码**，所以改那半就够了。
2. **能力位硬门：全群成员都确认支持才允许群主按。** 看着最"实"，但它会把功能按住：
   对端能力位只存在内存里（`peer_content_features`，重启即空），而群成员**离线是常态** ⇒
   大多数成员是 unknown。本仓已经明确反对把"不知道"算成"不支持"（`kind_audience` 的注释
   就是那次记账）：那样要么永远给按不了，要么提示永远在响。所以这一位只用于**如实说明**。
3. **静默事件行也开撤回。** 它们不在时间线上，"撤"它们不是离链而是**回滚那个动作**
   （撤 pin＝取消置顶？撤 reaction＝删表情？），而 `todo_update` 是 LWW 状态改动，撤回
   既不能让它倒退也没有东西可看 —— 要做得另立一套"群主否决"的语义，比本功能本身更大。
4. **系统提示行也开撤回。** 实测形状：`commands::insert_system_message` 里
   `msg_id = sys-<uuid4>` **每台设备各自生成、不广播**。拿它发撤回只有群主自己那台会消失，
   界面却写着"已撤回" —— 那是把假同步做进产品。
5. **顺手把收藏 / 系统通知 / @提醒一起改。** 撤回后这些残留是**已知缺口**（本次一并记档），
   但都不是"屏幕上还挂着已撤内容"这一条链：收藏是收藏者自己的快照与媒体副本（`favorites.content`
   / `media_path`），群主权限越进去就是动别人的数据。捆在一起做会把一批改动铺到 5 个领域上，
   回归面与这一批完全不成比例。

## 4. 它挡不住什么（诚实边界）

- **挡不住群主滥用**：没有申诉、没有远程审计、没有冷却。唯一的追溯路径是**每台设备本地**那份
  墓碑（`group_recalled_messages` 存 `recaller_id` + `seq`）。这是无服务器架构下的固有上限。
- **挡不住本地记录漂移**：每台比的是自己库里那份 `creator`。转让帧没送达 / 某台成员表落后时，
  同一批成员会判出不同结果，表现为"部分人那台没消失"。这与"版本旧"走同一句提示，不做额外区分。
- **不可逆**：墓碑是 G-Set（`INSERT OR IGNORE`，只增不减），所以**没有"撤回的撤回"**；
  要做只能另立"隐藏/恢复"两套语义，那是比本功能更大的一件事。
- **已知未修的残留**（记档，不在本 ADR 的承诺范围内）：会话预览本 ADR 修了；
  收藏快照与媒体副本、系统通知不撑销、@提醒指向、已撤回卡片在收藏里的呈现 —— 都还在。

## 5. 验证边界

实测（本地）：Rust `--features bluetooth --lib` 的 12 条撤回用例绿，含三张新判据
（授权矩阵 / 接收侧矩阵 / 接线与档位选择）；三发变异各自点名该红的那格 ——
拆掉跨会话闸 ⇒ 接收侧矩阵红在"作者本人也不许跨会话"；把群命令的选档退回永远 Author ⇒
接线判据红在"必须按本地 creator 现选档位"；接收侧不走那份统一判据 ⇒ 同一条红在计数那格。
前端 1468 条用例绿、`vue-tsc` + 构建绿。

未验（不许当成已过）：真机两端同时在线的撤回同步；离线成员重连后群主撤回帧经 outbox 补发
能否物化（走的是既有通道，没做端到端）；老版本对端确实丢弃并由那句提示覆盖的真实场景。
