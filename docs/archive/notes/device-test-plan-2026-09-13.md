## T1【最高优先】BLE 链路能不能活过 45 秒

**背景**：审计发现 BLE 读循环漏了回灌读活性 ⇒ 健康链路 15s 判不健康、45s 被看门狗拆掉。
本轮已修，需要你确认"真的不再自拆"。

**步骤**
1. 手机与 Mac 只开蓝牙（关 Wi-Fi），互相加好友、建立会话。
2. 保持两端都在前台，**什么都别做，静置 3 分钟**。
3. 第 2 分钟时，互相发一条消息。
4. 静置结束后，再互相发一条消息。

**期望**
- 3 分钟内**不应出现** `-conn peer=… 读活性超过 45s 无入站帧 ⇒ 拆除死链路`（这是"自拆"的标志）。
- 第 2 分钟那条消息应**立即送达**（不应等几十秒）。
- 链路徽标应一直显示"蓝牙直连"，不应时有时无。

**要贴给我**
- 两边日志里所有 `mesh` 与 `ble` 行（尤其 `[GATT]` / `-conn` / `[SEND]` / `[RECV]` / `[FRAG]`）。
- 如果第 2 分钟的消息延迟 > 2s，请贴时间戳。

## T2【最高优先】BLE 到底是什么速度（MTU 基准）

**背景**：文档里的"1KB/s、MTU=23"是**猜的**。本轮加了两条日志，可以一次测准。

**步骤**
1. 连上 BLE 后，在日志里搜 `[GATT] MTU 协商结果` 与 `[GATT] 外设侧 MTU 协商结果`。
2. 发一条**纯文字**消息（例如 10 个字），记录两端 `[SEND] … bytes=… 分片=n` 的 `bytes` 与 `分片`。
3. 发一张 **100~200KB 的图片**，秒表记「本机开始发送 → 对端看到图片」的墙钟时间。
4. 再发一张 **1MB 左右的大图**，同上（**很可能失败，见 T3，失败也是有效结论**）。

**期望 / 我要算的数**
- `每片有效载荷`（两条 MTU 日志）；
- 文字消息的 `分片数 ÷ 耗时` ⇒ 每片实际间隔；
- 图片的 `字节数 ÷ 耗时` ⇒ 真实 KB/s。

**要贴给我**
- 两条 MTU 日志原文；文字消息的 `[SEND]` 行；两次图片传输的起止时间与结果（成功/卡在"发送中"/报错文案）。

> 有了这三个数，我才能判断瓶颈是"MTU 没协商上"还是"每片 12ms 的节流"，
> 并据此决定要不要动 `NOTIFY_CHUNK_INTERVAL` 和主动 `requestMtu`。

## T3【高】大文件到底能不能传完（**已修，请你确认**）

**背景（旧结论已过期）**：以前 `file.rs` **固定 30s** 等 `FileCompleteAck`，而 1MB 的 256 个分块
在 1s 内就全部入队、`FileDone` 排在很后面 ⇒ 必然超时 ⇒ 每 5s 从头重传、`seq` 从 0 重来
⇒ 接收方报**「文件分片顺序错误」**。4.3.0（`324fa8f`）已改成**进展驱动**：
只要还有分块真的在往链路上写，就一直等；**只有安静 30s 没有任何写出进展**才算失败。
另外两处也修了：重传时接收方**丢掉旧状态重新开始**（不再回"重复的文件传输"）、
**迟到/重复的分片直接忽略**（不再整单失败）。

**步骤**：BLE 直连下依次发 **50KB / 200KB / 1MB** 三个文件（图片或文档都行），每个都要**等到出结果**
（成功或明确失败），别中途取消。

**期望（4.3.2）**
- 三个都**应当最终传完**（对端能看到文件、能打开；发送方不再卡在"发送中"）。
- 耗时随体积线性增长（BLE 慢是正常的，见 T2 算出真实 KB/s）；**1MB 可能要几分钟，请耐心等完**。
- 日志里**不应再出现** `文件分片顺序错误`。
- 只有**真断链/真丢包**才会失败，那时会看到 `接收方未确认文件完成`（发送方）——
  这条出现才算真失败，请把前后 20 行日志贴给我。

> 这一条现在是"确认修复"，不是"复现 bug"。传完了 = 修复有效；传不完 = 回归，请把日志给我。

## T10【顺手验，低优先】蓝牙开关的"手感"（4.3.1 修的）

**背景**：以前点蓝牙开关要干等 2~3 秒开关才动（前端在等后端，后端在等 CoreBluetooth）。
现在开关是**乐观更新**：先按你的意图动，再去后端启停；失败才回退并提示。

**步骤**
1. 设置 → 网络 → 点「蓝牙」开关（**关**）→ 再点一次（**开**）。
2. 稳定后，**1 秒内连点两下**（关→开）。
3. 故意制造失败（可选）：Android 上把「附近的设备」权限拒掉后点开。

**期望**
- 开关**当帧就滑过去**，滑杆上出现一枚小转圈；**最多 2~3 秒**转圈消失。
- 连点两下后，开关**停在最后一次的选择上**（= 开），不会"点了没反应"。
- 权限被拒时：开关先动 → 然后**回退**成原样 + 一条错误提示（这就是"失败回退"，不是 bug）。

**判读（日志里搜这几条）**
| 日志 | 含义 |
|---|---|
| `蓝牙通道切换：已停止 → 开启` | 一次**真实**启停（每次点击最多一条） |
| `蓝牙通道开关进入冷却：等待 Nms 后执行（合并抖动）` | 第二次点击被**排队**（不是丢弃）——连点测试应当看到这条 |
| `运行状态已经是目标状态（幂等）` | 重复请求被幂等挡掉（没有多拆一次蓝牙栈） |
| `忽略高频蓝牙通道切换请求` | ⚠️ **旧行为**：看到它就说明你装的不是新包（≤4.3.0） |

## T12【必做·先做这个】三端身份与"谁拨谁"（4.3.6 修的身份 bug）

**背景**：安卓的 `device_id` 曾经多套一层 `dev-` 前缀（`dev-gosslan-…`），而桌面端是
`gosslan-…` ⇒ `'d' < 'g'` ⇒ **那台安卓在三端里恒为最小 id** ⇒ 按「大 id 拨、小 id 只接受」
的镜像规则**它永远不主动拨号**，只能等别人来连它。已修，且对**已装设备做就地迁移**（不必清数据）。
但 device_id 是**持久化**的：不确认一次，后面所有"谁连谁"的结论都不可信。

**步骤**
1. 三台设备都装 4.3.6（Windows 那边从 `next` 重打），**只开蓝牙**，互相同一房间内。
2. 打开一次「添加好友」（会立刻触发一轮扫描），然后在**每台**的运行日志里搜 `gosslan-`
   与 `本机蓝牙适配器地址`。
3. 任两台之间互相加好友（先安卓↔Windows，再 Mac↔安卓）。

**期望 / 判读**
- 三台自己的 id **都必须是 `gosslan-<16 位十六进制>`**；出现 `dev-gosslan-…` ⇒ 迁移没跑到
  （多半是旧包或没重启）⇒ 告诉我。
- 安卓**不需要清应用数据**：装上 4.3.6 → 杀掉再开一次 → 日志里的 id 应该已经变成 `gosslan-…`。
- 任两台之间：**id 大的那一方**发起连接（日志 `[DISCOVERY] 候选可拨 … ⇒ 开始连接`），
  另一方出现外设侧事件；最终两侧都应有 `[SESSION] 已就绪`（双向 Hello 已验签）。
- 若 id 小的一方**始终没有**任何"被连入"的痕迹，而 id 大的一方也没有"开始连接" ⇒ 把两侧日志给我。

## T13【必做】Windows 外设角色：安卓/Mac 能不能发现并连入 Windows

**背景**：Windows 以前只做 central（**不能广播、不能被连**）⇒ 手机永远发现不了它，
而镜像护栏又让 id 较小的一方不主动拨 ⇒ 两侧都在等对方。这一轮补了 WinRT
`GattServiceProvider` 外设角色，并顺带修了"广播报成功但没人看得见"（显式 `SetIsDiscoverable`
+ 盯住广播状态）。**这一步是"手机↔电脑 mesh"在 Windows 上的结构性验收。**

**步骤**
1. Windows 从 `next` 打包安装（`npm run dist`），只开蓝牙。
2. Windows 日志里确认外设角色真的起来了：搜 `外设角色已启动` / 广播状态（`Started`）；
   并记下 `本机蓝牙适配器地址 = …`（后面用来区分"自己/对端"）。
3. 安卓与 Mac 各打开一次「添加好友」（触发立刻扫一轮），在扫描日志里找 Windows：
   `[DISCOVERY] 候选可拨 id=… ⇒ 开始连接（GATT central）｜rssi=… 地址类型=… 名字=… 命中=<UUID>`
4. 任一方点「加好友」，看两侧的握手链路：
   `[GATT] 已就绪` → `[GATT] MTU 协商结果 …` → `[SESSION] 已就绪`。
5. 连上后互发：一条文字 + 一张 100KB 左右的图片（顺便给 Windows 的通知节流取数，见 T2 的方法）。

**判读（关键日志 → 含义）**

| 日志 | 含义 / 下一步 |
|---|---|
| 安卓/Mac 压根没有 Windows 的候选行 | Windows 广播仍不可见 ⇒ 贴 Windows 的广播状态日志（`Aborted` / `StartedWithoutAllAdvertisementData` 都要贴） |
| 有候选行但 `命中=(未在本设备广播里看到我们的 UUID)` | 对端广播里**没有**我们的服务 UUID ⇒ 广播数据不完整（不是射频问题） |
| `[DISCONNECT] 连接失败（第 n/3 次）：Not connected｜系统链路状态：连接前=… 失败后=false` | 射频层没连上（对端没在监听 / 超出范围 / 适配器问题）——对照 T2 的地址类型 |
| `连接失败…失败后=true` 或 `发现 GATT 服务失败` | 连上了但 GATT 数据库还没就绪（重试应当覆盖；若持续失败把日志给我） |
| 两侧都有 `[SESSION] 已就绪` 但发消息不通 | 走 T1/T3（读活性/文件链路），并贴 `[SEND]`/`[RECV]` |

⚠️ Windows 外设侧的**通知节流是 12ms**（与安卓同参数，但**没有 Windows 真机 A/B 数据**）：
这条测试顺手记下"100KB 图片的实际耗时"即可，我据此再决定要不要按对端节奏自适应。

## T14【必做】对方重装/换设备后重新加好友（**不用重启**）

**背景（用户 2026-09-13 真机）**：两台电脑本来是好友；Windows 清空数据重装后再加 Mac，
Mac 的聊天里出现"⚠️「…」的身份密钥发生变化"的系统提示；此后**两边都收不到消息、也收不到好友申请**，
而且"删掉好友重新加"也没用 —— **必须重启**才好。
根因：解除关系只删了 `friends` 表那一行，内存里那条**广播学来的旧公钥**还在当信任根用
（`verify_hello` 会回落到它）⇒ Hello 一直被硬拒。已修：解除关系就解除身份绑定。

**步骤（请在**同一对设备**上完整走一遍，别跳过任何一步）**
1. A、B 两台已是好友且能互发消息。
2. **B 清空应用数据**（或用另一台干净设备）后重新安装同一版本，两台都保持在线。
3. 观察 A 的聊天窗口：应出现系统提示「…身份密钥发生变化…」（**这是对的**，不要慌）。

## T9【Mac 专项】鼠标拖选文字选不中（用户 2026-09-13：Mac + **纯文字**也会）

已排除的两个原因（所以不用再怀疑它们）：
- **不是表情图片被拖走** —— 纯文字消息同样复现（用户已确认）。
- **不是内边距锚点** —— 气泡根已加 `select-text`（上一轮修复），仍是同样表现。

剩下的可能只剩两类：**① 全局层面的 WebView/系统行为；② 我们这个页面的 DOM 结构**。
下面两步能把范围**一刀切开**，请按顺序做。

### 第一步（不用重新打包，1 分钟）

在**同一个 app、同一台 Mac**上，分别尝试用鼠标拖选：

1. **运行日志**窗口里的一行日志；
2. **设置 → 关于**里的设备指纹；
3. 一条长文本消息 → 点「展开」→ 在**弹窗**里拖选那段文字；
4. （对照）聊天区气泡正文 —— 已知失败。

**判读**
- 若 1/2/3 **有一个能选中** ⇒ 问题只在我们**消息行**这块 DOM（我继续按 DOM 方向查，
  重点查虚拟列表的行容器与 `user-select` 继承）；
- 若 1/2/3 **全都选不中** ⇒ 是 **WKWebView / Tauri 全局**层面的问题（下一步）。

### 第二步（需要重新打包一次，验证一个具体假设）

最可疑的全局因素是 `src-tauri/tauri.conf.json` 里的 `"dragDropEnabled": true`
（wry 会把 WKWebView 注册成 `NSDraggingDestination`，可能与 WebKit 自己的选区拖拽打架）。

我已经准备好一份**只改这一个开关**的覆盖配置（没有改主配置，随时可丢）：

```bash
cd src-tauri
CARGO_HOME="$PWD/target/cargo-home" \
  npx tauri build --features bluetooth --target aarch64-apple-darwin --bundles app \
  --config tauri.nodrop.conf.json
bash ../scripts/pack-macos-app.sh aarch64-apple-darwin
```

装上这个包后再拖选一次：

- **能选中了** ⇒ 确认是 `dragDropEnabled` 的副作用。接下来是一个取舍：
  关掉它就**失去"把文件拖进聊天框发送"**（那是 Tauri 原生拖放提供的真实路径）。
  可以做的折中：默认关、在设置里给个开关；或保留原生拖放但另找选区方案。
- **还是选不中** ⇒ 那就是 macOS/WKWebView 层面的（已知 macOS 15 有一条选区回归），
  我会转去查系统版本 + wry 版本的已知问题，不再在 CSS/DOM 上耗。
