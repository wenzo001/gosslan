# BLE 首轮稳定性审计（Mac ↔ Android，P0）

- Date: 2026-09-13
- 范围：**只做 Mac ↔ Android、只用 BLE（无局域网 / 无 Tailscale）** 的
  发现 → 连接 → 会话 → 好友 → 消息 → ACK 闭环。
- 基线：`next` @ `f497f99`（4.2.13，含 4.2.12/4.2.13 两个链路修复）
- 方法：读代码 + 真机日志（Mac：`~/Library/Application Support/com.gosslan.app/logs/gosslan.log`；
  Android：`adb logcat -s gosslan:I`、`dumpsys bluetooth_manager`）+ 本机对照实验。

## 1. 当前 BLE 架构图

```
AppState
 ├─ ble: Option<BleHandle>            （network/ble.rs::start/stop，feature = "bluetooth"）
 ├─ links: peer_id -> Vec<Link>       （**统一链路表**：LAN / Routed / Bluetooth 同表）
 ├─ peers: device_id -> Peer          （发现到的节点；BLE 侧只有握手成功后才进表）
 ├─ ble_no_dial: HashSet<地址>         （"不要再拨"名单：对端是指定拨号方时登记）
 └─ ble_dial_failures: 地址 -> (次数, 下次允许时刻)   （指数退避）

network::ble
 ├─ scan_loop         每 10s 扫 3s（driver::scan_peers）→ 过滤 → dial_and_register（每候选一个任务）
 ├─ dial_and_register central 侧：driver::connect → Hello 往返验签 → 去重/镜像判据 → 登记 Link
 │                    → spawn ble_writer_loop / ble_reader_loop → flush 全部待发队列
 ├─ peripheral_accept_loop  外设侧：PeripheralEvent::Frame →（路由投递 | 握手）
 │                    → try_accept_handshake：验签 → 回 Hello → 登记 Link → flush
 ├─ ble_writer_loop / ble_reader_loop   帧级收发（**与 LAN 同一份 Message / 同一个 handle_message**）
 └─ driver（transport/bluetooth.rs）
       ├─ adapter()            btleplug Manager → 第一个适配器（Android 先查 droidplug 就绪）
       ├─ scan_peers()         ScanFilter::default() + 按 properties().services 过滤（不用平台过滤）
       └─ connect()            connect → discover_services → 取 RX/TX 特征 → 订阅 notify → BleConnection

Android 外设侧：transport/ble_android.rs（JNI）↔ Kotlin BlePeripheral.kt（BluetoothGattServer）
macOS  外设侧：transport/bluetooth_peripheral.rs（CoreBluetooth / objc2）
```

**关键事实**：BLE **没有自己的消息协议**——线上还是同一个 `Message`（`serde_json`），
同一个 `handle_message`、同一个 E2EE、同一个 outbox/ACK。BLE 只换"怎么把帧送过去"。

## 2. Discovery → Connection → GATT → Session → Send 的实际调用链

| 阶段 | 代码位置 | 何时算完成 |
|---|---|---|
| Discovery | `ble.rs::scan_loop` → `driver::scan_peers` | 拿到含本服务 UUID 的广播（每 10s 一轮，3s 窗口） |
| Connect(GATT) | `ble.rs::dial_and_register` → `driver::connect` | `connect()` + `discover_services()` + 取到 RX/TX 特征 + **订阅 notify** 全部成功 |
| Session(握手) | 同上：发 Hello → `read_one` 读对端 Hello → `verify_hello_for_ble` | 双向 Hello 验签通过 |
| Link ready | `register_connection(...)` + `Link{path_kind: Bluetooth}` 进 `links` | 写/读循环已 spawn，UI 的 `Peer.link == "bluetooth"` |
| Send | `commands::send_message` → `insert_message_and_outbox` → `has_link? try_send : broadcast_gossip` | 帧进 Link 的优先/普通通道，由写循环发出 |
| ACK | 接收方 `handle_message` 落库后 `try_send(Ack)` → 发送方 `Message::Ack` 分支 | 发送方按 msg_id 命中 outbox 并置 delivered |

## 3. 三个真机症状的根因（带证据）

### 3.1「已搜到，但未连接」/ 好友申请**等 5～6 分钟**

**主因：拨号退避上限 10 分钟 + 只有一侧会拨，把暂时性失败放大成分钟级故障。**

`ble.rs::ble_dial_backoff_ms`（旧值）：`60s → 120s → 240s → 480s → 600s`（封顶 10 分钟），
按 **BLE 地址**记账，只有 `dial_and_register` 成功才清零（`clear_ble_dial_failure`）。
而"小 id 只接受"（`should_dial_ble`，`ble.rs:298`）意味着**另一方永不主动拨** ——
于是唯一的拨号通道一旦连续失败，就被自己的退避锁死到分钟级。
日志里当时只写 `候选 X 未建立链路：…`，**完全看不出"其实是被退避锁住了"**。

叠加的链路层 bug（4.2.12/4.2.13 已修，仍在你的 4.2.11 上生效）：
- 重连时新连接的 Hello 被投给**旧链路**的管道（对端报 `对端首帧不是 Hello`/`握手超时`）；
- 链路一断就 `mark_peer_offline` **删节点**，「添加好友」列表数据源就是它 ⇒ 只闪一下。

**好友申请本身的可靠性是对的**：`send_friend_request` 先登记 `pending_out_requests`，
Hello/建链时 `flush_pending_friend_request` 补发（`transport.rs:2053`）。
但它**只在"建链"时补发**，不在心跳时补发 ⇒ 链路活着、这一帧丢了的话，要等下一次建链。

### 3.2「接受了，但对端好友状态不同步」

**根因：`FriendAccept` 只发一次，且没有回执、没有重发。**
`commands.rs::accept_friend_request`（旧代码）：`has_link ? try_send : broadcast_gossip` 各一次，
然后 `forget_pending_request` + `Ok(())`。**广播在"一个直连都没有"时是静默无操作**，
发送方也无从知道失败 ⇒ 单边好友关系（我这儿有他、他那儿没我），永久。

### 3.3「消息一直发送中」

消息**不是丢了**：`send_message` 一律先落 `outbox`（`insert_message_and_outbox`，INV-003），
再 `try_send`/`broadcast_gossip`，投递失败**故意不返回 Err**（避免前端重发）。
UI 的"发送中" = **没收到 Ack**。所以它卡住只能是三种之一：
1. **没有链路**（3.1 的病根）⇒ 帧发不出去；
2. 链路在，但**帧丢了**（BLE 写成功≠送达）；
3. 对端落库了但 **Ack 丢了**。

好消息：这三种**都不会永久卡死** —— 接收方对**重复投递会再次回 Ack**
（`transport.rs:2446` 的 `exists` 分支），而发送方的 outbox 会在下一次
Hello/心跳时 `flush_outbox` 重发。**所以"发送中"的持续时间 = 链路恢复时间**，
而不是"ACK 机制坏了"。真正要修的是 3.1 的链路可用性与恢复速度。

### 3.4 假在线（"蓝牙直连" ≠ 一定能发）

`Peer.link == "bluetooth"` 是 `fill_peer_links` 从 `links` 表填的，而 Link 只在
**双向 Hello 验签通过并 spawn 收发循环之后**才登记 ⇒ 它其实已经隐含"GATT 连接 + 服务发现 +
订阅 + 会话握手"全部完成，比 UI 显示的强。
**真正的缺口是"已发现（未建联）"这一档**：此时点「加好友」只是把消息**登记进待发队列**
（这是对的），但界面会说"已发送"——**用户看不出"其实还在等链路"**。
本轮不改 UI 语义（属于第二轮），但把 BLE 生命周期日志补齐，让这条链路变得可观测。

## 4. 本轮最小修复（只动 BLE 接入链路）

| # | 修什么 | 位置 | 为什么 |
|---|---|---|---|
| 1 | 退避 **5s→10s→20s→40s→60s 封顶**（原 60s→…→600s） | `ble.rs::ble_dial_backoff_ms` | 把"暂时性连接失败"从 5～10 分钟压回 1 分钟内（真机的 5～6 分钟延迟主因） |
| 2 | 对端**拨我们成功**时也清退避 | `ble.rs::try_accept_handshake` | 对端能连上 ⇒ "我拨不上它"的历史已过期；否则唯一拨号方会被自己的退避锁住 |
| 3 | 跳过退避时**留痕**（含剩余毫秒） | `ble.rs::scan_loop` | 原来只看到"未建立链路"，看不出被退避锁住 |
| 4 | **`FriendAccept` 有界补发**：2 分钟窗口 / 最多 3 次 / 两次至少隔 5s | `commands.rs::send_friend_accept_via_link`（抽出）+ `transport.rs::flush_pending_friend_accept` + `state.rs::pending_out_accepts` | 修"接受了但对端状态不同步"的永久单边好友 |
| 5 | 好友申请/同意回执**也在心跳时补发** | `transport.rs` 的 `Heartbeat` 分支 | 链路活着但上一帧丢了时，不必等下一次建链 |
| 6 | BLE 生命周期日志 | `ble.rs` + `transport.rs` | 用户要求；见下节 |

**明确没有动**：`msg_id` / E2EE / X25519 / ChaCha20-Poly1305 / Ed25519 / SQLite 结构 /
outbox 语义 / ACK 语义 / 好友表结构 / LAN / Tailscale / 文件传输 / UI 结构 / 线格式。

## 5. 新增日志（可 grep 的生命周期轨迹）

```
[DISCOVERY] 候选可拨 id=… ⇒ 开始连接（GATT central）
[DISCOVERY] 跳过候选 id=… 原因=退避中 剩余=…ms
[CONNECT]   开始连接 ep=…（connect → service discovery → subscribe）
[GATT]      已就绪 ep=…（连接 + 服务发现 + 通知订阅都成功）
[SESSION]   已就绪 peer=… ep=…（双向 Hello 已验签，transport 可用）
[SESSION]   已就绪（外设侧）peer=… ep=…
[SEND]      type=… msg_id=… → peer=… ep=… bytes=…
[SEND]      写失败 ⇒ 结束该链路写循环 …
[RECV]      type=… msg_id=… ← peer=… ep=… bytes=…
[ACK]       已持久化 ⇒ 回执 msg_id=… → peer=…
[ACK]       重复消息仍回执 msg_id=… ← peer=…
[DISCONNECT] 候选 … 未建立链路：…（已进入退避）
```

`Heartbeat` / `Presence` / `UserInfo` 被过滤（每 5s 一条，打进来会把日志刷满）；
`type=` 走 `Message::wire_kind()`（与 serde tag 同一份事实来源）。

## 6. 20 个问题的答案（要点）

1. **发现**在 `scan_loop` → `driver::scan_peers`（每 10s / 3s 窗口）。
2. 发现后**立刻**拨（`dial_and_register`，每候选一个 tokio 任务，不阻塞下一轮扫描）。
3. **是**两个状态：`peers`（发现）vs `links`（已连接）；UI 文案分别是"已发现（未建联）"与"蓝牙直连"。
4. 发起 GATT connection：`dial_and_register`（central，btleplug）。
5/6. 接受入站：Android `BlePeripheral.kt` / macOS `bluetooth_peripheral.rs` → `peripheral_accept_loop`。
   transport ready = **双向 Hello 验签 + Link 登记**（此时 GATT 连接/服务发现/订阅都已完成）。
7/8. service discovery 与 notify 订阅都在 `driver::connect` 内，**先订阅再握手**；
   订阅失败 ⇒ 连接直接失败（不会出现"写成功但收不到"）。
9. 协议会话：没有独立握手阶段，就是 `Hello` 双向验签（复用 LAN 的那套）。
10. E2EE：不建会话；每条消息用对端 X25519 公钥现算 shared secret（`send_message`）。
11. Friend Request：`commands::send_friend_request` → `send_friend_request_via_link`（Gossip 定向）。
12. 可能在 transport 未 ready 时发送吗？**会**，但**不会丢**：先登记 `pending_out_requests`
    （`commands.rs:1397`），建链/心跳补发。
13. 未 ready 时进可靠队列？**是**（同上，复用 outbox 机制的姊妹实现，不另造一套）。
14. 断线自动重连？**是**：`scan_loop` 每轮重扫 + 重拨（受 `ble_no_dial` 与退避约束）。
15. 重连后 outbox 重新 flush？**是**：`dial_and_register` / `try_accept_handshake` 末尾
    与 Hello 分支都会 flush（outbox/群/已读/群密钥/文件/好友申请/同意回执）。
16. 消息是否一定过统一 transport/router？**是**：`send_message` → outbox → `try_send`
    （按 `links` + 选路）或 `broadcast_gossip`（MeshRouter 定向/洪泛）。
17. ACK 能通过 BLE 返回？**能**：`Ack` 就是普通 `Message`，走同一条 Link。
18. BLE 收到的数据是否进现有处理链？**是**：`ble_reader_loop` → `handle_message`（与 LAN 同一入口）。
19. 假在线？**"蓝牙直连"不假**（见 3.4），但**"已发现未建联"时界面会乐观说"已发送"**，
    用户看不出在等链路 —— 这是本轮**记录**、下一轮改 UI 的点。
20. connection object 已建但 notify 不可用？**不会**：订阅是 `driver::connect` 的组成部分，
    失败即 `Err` ⇒ 不会登记 Link。

## 7. 真机测试方法（P0）

```
前置：两端 ≥ 4.2.14；关 Wi-Fi；只开蓝牙；清空数据各一次
Log：Mac  ~/Library/Application Support/com.gosslan.app/logs/gosslan.log
     Android  adb logcat -s gosslan:I
判据（Test A~F）：
  A  Mac ↕ Android 连做 10 次：清数据 → 启动 → 等自动发现 → 加好友 → 接受 → 发 "1"
     要求 10/10；每次都能在日志里看到 DISCOVERY → GATT → SESSION → SEND/RECV → ACK
  B  已是好友：关蓝牙再开 → 自动发现/连接/session ready → 能发消息（不需重新加好友）
  C  连接过程中点「加好友」→ 不能丢：pending → 建链/心跳 → 自动送到
  D  连发 "1".."5" → 5/5 到达 + 5/5 ACK
  E  双向同时发 → 不死锁
  F  传输中断开 → outbox 保留 → 重连 → 重发 → ACK → 清 outbox
```

## 8. 本轮未做（按用户要求推后）

- Windows BLE（phase 2；本机无法交叉编译验证，见被 stash 的准备工作）；
- 「已发现」与「可用」的 UI 状态细分、中继发文件（B 方案）。
