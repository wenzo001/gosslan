## 1. 审批结论

**建议：有条件通过工程设计评审；不把本结论当作当前版本发布签字。**

产品目标与架构主线总体一致：无账号、无中心服务、局域网/蓝牙发现、点对点传输、本地持久化与强制端到端加密。README 对跨网中继、Android 后台条件、无云同步等边界有说明；架构文档也把权限、持久化与协议不变量落在后端。这些是清晰且互相支持的选择。

项目的主要风险不是缺少规范，而是系统复杂度、规范/证据维护成本及若干关键运行场景仍需要独立验证。仓库规模已经包含多平台传输、Gossip、中继、BLE、断点续传、群管理、更新器、多个窗口和大量定制验证工具。对于“轻量、无服务器的本地通讯”产品，这种范围可以成立，但应由用户需求和真实设备可用性持续证明，不能因机制已实现就视为用户价值已验证。

**审批条件：**

1. 高风险安全审计条目应以当前代码和当前提交为准逐项关闭；本报告只把 10 月旧审计当作线索。
2. 发布判断补齐平台真机、升级/恢复和关键 UI 的人工验收凭据；模拟测试不能代替它们。
3. 设计语言研究稿与强制规范继续明确分层；把已确认的决策及时归并，避免两套规范并行漂移。
4. 定期按用户任务审查功能面和维护成本，避免为了架构完整性持续增加用户不需要的设置与流程。

## 2. 产品目标与架构一致性

| 产品承诺 | 架构落点 | 判断 | 需要持续核实的边界 |
| --- | --- | --- | --- |
| 不注册、不依赖中心服务 | 本地设备身份、UDP 发现、TCP/BLE，跨网时可选自托管哑中继 | 一致 | 中继是明确的可选例外；部署与可达性需要用户自备和双端配置，不能宣传成默认跨网可用 |
| 消息端到端加密恒开 | X25519、Ed25519、ChaCha20-Poly1305；密钥和消息本地存储 | 一致且属于核心产品信任 | 密钥身份绑定、设备迁移/丢失恢复是用户理解成本；无云备份是隐私收益也是数据恢复限制 |
| 离线可发送、恢复后补发 | 本地 outbox、确认、重试、消息 ID 去重 | 一致 | “离线也能发”应理解为本机排队；最终送达依赖对端再次在线和兼容协议 |
| 三平台互通与附近发现 | Tauri/Rust 共用协议，平台原生 BLE/权限桥 | 方向一致 | 平台权限、后台限制、蓝牙角色和网络环境差异使“同一体验”不能只靠共享协议保证 |
| Android 后台接收 | LAN 通道开启时以前台服务维持，常驻通知可停止；不承诺 Doze/开机自启 | 边界诚实 | 必须持续在目标 OS 与厂商设备上验证；用户可能把“后台可收”理解为总是送达 |
| 群工作区、任务和文件 | 群消息/密钥/成员/管理员/历史同步/任务/群文件多条状态流 | 产品扩展一致，但显著增加心智负担 | 首次使用需要解释群主、管理员、在线成员快照、历史补拉和文件终态；检查默认路径是否仍然直观 |
| 无云备份、不合并多设备历史 | 本地 SQLite、导出 Markdown、设备独立身份 | 一致 | 导出并非完整备份；新设备迁移、数据库损坏与私钥丢失的预期应在产品内清楚呈现 |

### 产品层面的设计判断

- **定位明确，功能面偏宽。** 消息、群协作、文件中转/续传、共享目录、任务看板、拓扑诊断、更新器和多种连接路径汇聚到一个产品。建议以“首次加好友并可靠发出第一条消息”“恢复后完成离线投递”“找到并打开收到的文件”三条核心任务作为删繁标准。
- **隐私与可恢复性存在有意取舍。** 数据本地化降低服务端暴露面，但没有云恢复/跨设备历史合并。应把“导出不是完整备份”和设备身份不可替代的后果放进用户可见的设置/帮助流程，而不是只留在开发文档。
- **可靠性承诺比网络现实更容易被用户高估。** 局域网组播、蓝牙、NAT、中继和移动后台都受环境限制。界面应显示连接路径与可达状态，并区分“已排队”“已送达”“对端已读”；仓库的不变量对此有良好基础，仍需真机验收来验证文案和状态一致。

## 3. 架构评审

### 做得扎实的部分

- 前后端职责大体清楚：Vue/Pinia 负责界面状态，Rust/Tauri 命令层承接系统能力，SQLite 是持久状态来源；文档明确禁止前端维护第二份权威业务状态。
- 协议、E2EE、outbox/ack、会话归属和数据库迁移有专门不变量与 ADR，关键决定能追溯到验证入口。
- 网络身份与端点分离、多路径链路、优先级队列、内容生命周期分层，符合 P2P 系统需要；慢 IO 离开异步 worker、锁作用域和错误码也有较明确规范。
- 多平台桥接并未假装“共用 Rust 就等于跨平台验证完成”：Android JNI/R8、macOS 沙盒、Windows 安装和 WebView 均有专门检查与注意事项。
- CI 与本地工具对测试清单、i18n、文档数字、护栏非空转和变异自证有较高投入，避免了不少静默失效。

### 主要架构风险与建议

1. **复杂度和单人心智负担偏高（中高）。** 大量冻结规则、历史审计、专用脚本和跨文件锚点降低了随意改坏的概率，但提高了新贡献者和产品迭代的进入成本。建议围绕领域入口维护短而稳定的“权威地图”，旧审计明确状态、日期和复核命令；定期清退重复、已关闭或不再有判定价值的资料。
2. **文本/形状护栏易过度依赖实现外形（中）。** 这类护栏适合守接线、配置与难以构造行为的边界，但不应成为安全语义的主要证明。重要身份授权、权限拒绝、持久化顺序优先通过生产函数的行为测试或端到端协议验证，源码形状只负责补充。
3. **跨平台证据存在结构性缺口（高，发布风险）。** macOS/Windows/Android 的系统权限、后台服务、WebView、升级器和文件打开均不是单元测试可完整覆盖。将测试格明确标为自动/模拟/手工真机，并设置平台发布门槛；没有凭据的格保留 NOT RUN。
4. **模块/决策规模需约束扩张。** 拓扑、诊断与开发者可观测性对维护有价值，但要避免它们侵占主聊天路径、增加默认启动成本或扩大权限面。新增能力要求说明：目标用户、默认关闭/开启理由、数据边界、降级方案和删除条件。
5. **文档权威有分层，但状态仍可能陈旧。** `AI_PROJECT_HANDOFF.md` 指定代码/测试优先，设计语言 README 明确为研究基线而非强制规则；日期审计中的“已修/未测”容易被脱离上下文引用。建议统一每份活审计的状态字段：基线、复核提交、状态、证据命令、未覆盖范围。

## 4. 设计系统与界面代码评审

### 优点

- `docs/design-guidelines.md` 给出了圆角、同心关系、焦点、无障碍和动画的强约束，令牌集中在 `src/style.css`，避免单页随意发明视觉规则。
- `docs/design-language/ux-criteria.md` 将稳定性、流畅性、正确性、原生体验和安全性放在视觉偏好前，并有键盘、触控、对比度、错误态和窄屏的验收锚点。
- 设计稿明确玻璃属于控制层、正文保持实色，且考虑低端设备、减少透明度和移动端动画；与通讯产品强调可读性的目标一致。
- 项目保留原生窗口、系统通知、平台权限等边界，没有强行以纯 Web UI 替代系统能力。

### 可改进处

- **研究文档与强制规范需要更短的晋升路径。** `docs/design-language/README.md` 明确自身是 2026-11-05 的研究基线、不是强制规范，并列出玻璃/按钮/输入框差距及若干需确认项目。建议对每项标记“采纳、拒绝、待决”，决策完成后只在规范保留最终规则，研究细节留为历史依据。
- **存在规范密度过高的风险。** G-1～G-16、设计指南、玻璃/控件/动效专项说明以及 `designs/gosslan-redesign` 多套资产可能形成多重事实源。明确当前生产 UI 的唯一规范、当前采用的设计稿版本和被弃用稿，避免开发人员从设计目录直接拷贝陈旧 token。
- **统一组件与业务差异要平衡。** 统一按钮/输入框可提升一致性，但迁移需按可访问性、尺寸、键盘/触控和错误语义验收，不宜仅以 import 数或样式计数作为完成标准。
- **视觉动效的成本要在真实设备上测。** 透明、模糊、色雾与转场可能影响低端 Android、电量、滚动和文本可读性；CSS/Chromium 截图不能替代 WKWebView、WebView2 和 Android WebView 的实机表现。
- **设计语言的外部依据要分清事实与推断。** 设计参考目录已登记来源，这是好做法；所有“平台规范明确要求”类措辞应保留对应原始来源、适用平台和置信度，个人风格判断标作建议而不是平台规则。

## 6. 最佳实践改进计划

### P0：发布前可信度与安全闭环

1. 以当前 HEAD 复核旧审计中所有 High 项，逐项记录“仍成立/已修复/设计使然/证据不足”。
2. 对 FriendAccept、Gossip 身份锚点、私钥边界、群/文件授权、路径归属等信任边界，以生产逻辑行为用例和正反对照验证；确认安全审计能在 PR 上执行。
3. 补齐 Win/macOS/Android 真机矩阵：好友建立、离线补发、群聊/群文件、文件打开、权限撤销、后台接收、升级覆盖和崩溃恢复。缺少真实设备的格明确标阻塞或未测。
4. 对外产品文案与 UI 状态核对：离线排队≠送达、局域网发现≠跨网可达、Android 后台收取受系统策略限制、导出≠备份。

### P1：架构与质量治理收敛

1. 为每个安全/数据不变量明确首选证明类型：行为测试优先，集成/协议测试其次，源码形状作接线补充；每条护栏保留一个能证明扫描活性的反例。
2. 盘点主线程、tokio worker、全局 DB 锁、文件 IO 与大对象内存预算，优先修复会阻塞用户操作的高影响路径，并用慢盘/大文件实测。
3. 收敛跨层规则的事实源：消息类型/可转发性、权限状态、错误码、平台能力与更新资产映射由单一语义判定驱动，并维持跨语言契约测试。
4. 发布 CI 报告中区分“构建通过”“模拟通过”“真机通过”；所有定时任务/非 PR 护栏列出覆盖频率与最长反馈延迟。

### P2：产品与设计系统精简

1. 选择 3–5 条核心用户旅程做可用性验收，针对首次连接、好友安全码、离线状态、文件收取和数据恢复收集真实用户反馈。
2. 对群任务/拓扑/共享目录等扩展能力分别评估使用频率、设置复杂度与维护成本；低频能力考虑渐进呈现，避免主聊天流程承担全部功能密度。
3. 建立设计决策台账：每项候选改动有动机、可访问性与性能影响、跨平台证据、决策状态和复查日期；确认后回写一处规范。
4. 对 390px、桌面窄窗、亮/暗、键盘导航、减少动效和低端设备形成稳定截图/真机基线；视觉一致性不可替代可读性与功能状态正确性。

### P3：持续维护

1. 每次主要阶段转换更新审计状态与复核提交；已解决项从当前风险列表移入历史，不复制未更新的行号。
2. 季度检查 ADR 状态、文档链接、过期设计稿和验证脚本价值；删除/归档前确认没有活跃约束依赖。
3. 追踪质量指标的趋势而非堆叠单次数字：回归逃逸率、关键旅程完成率、崩溃/卡死、后台送达率、升级成功率、跨平台差异和未测矩阵比例。
