# 身份私钥的威胁模型（2026-10-24，审计 SEC-09 决策记录）

## 一、结论（用户裁决）

**不引入 `keyring` 依赖**，保持"私钥 base64 存 SQLite + 文件权限收紧"的现状，
把威胁模型写清楚。触发重新评估的条件见 §五。

## 二、现在存在哪里

| 项 | 位置 | 保护 |
|---|---|---|
| `x25519_secret` / `ed25519_secret` | SQLite `settings` 表，base64 文本（`state.rs::persist_identity`，同一事务写入两条） | 主库 `0600`、`-wal`/`-shm` `0600`、app data 目录 `0700`（`private_fs`） |
| 迁移前备份 | `<stem>.pre-v…-to-v….db`，保留最近 3 份 | 构造时 `0600`（`db::migration_tests::init_tightens_database_sidecars_and_backup_to_owner_only`） |
| 运行日志 / 崩溃现场 | `logs/` | 目录 `0700`、文件 `0600`、轮转后保持（`logging` 的权限用例） |

Unix 上 `0600`/`0700` 的语义：**只有属主（和 root）能读写/进入**。
`0600` 挡的是"同机另一个用户"，不是"同一用户的另一个进程"。

## 三、挡得住什么、挡不住什么

**挡得住**

- 同机其他 Unix 用户直接读库/侧车/备份/日志（含 `ls` 出目录内容 —— 目录 `0700`）。
- 数据库文件被普通备份工具以**其他用户**身份读取。
- 应用自身把权限写成 `0644` 的那类回归（已由权限用例钉住）。

**挡不住**（都是已知、接受的边界）

- **同一用户态的任意进程**：恶意软件、被注入的编辑器插件、以同一用户跑的脚本，
  读 `~/Library/Application Support/…/gosslan.db` 与读自己的文件没有区别。
- **root / 管理员 / 获得完整磁盘镜像或 Time Machine 快照的人。**
- **进程内存转储**：启动后私钥就在内存里（任何使用方式都如此，不因存 Keychain 而改变）。
- **用户自己**主动拷贝/上传数据库。
- 另外要记住：**本地库里还有全部消息明文**（`messages.content`）。即使私钥被保护，
  读库本身已经能拿到会话内容 —— 私钥保护不是"库被读"的唯一后果。

## 四、私钥泄露的影响面

- 冒充本机身份与好友握手（`Hello` 用 ed25519 签名）；
- 解密**未来**用本机 x25519 公钥封装的文件会话密钥（历史文件密钥不落库）；
- 不能解密已删除的临时会话密钥，也不能伪造对端签名。

所以它是"身份长期凭据"，不是"历史消息总钥匙"；这也决定了它值得保护，但
在"同用户态恶意进程"这个威胁下，Keychain 也挡不住（同用户进程同样能读 Keychain
条目，除非用户每次启动都手动确认 ACL —— 那与"开机即用"的产品目标冲突）。

## 五、为什么不引 `keyring`（以及何时改主意）

不引的理由

1. **威胁模型上收益有限**：`keyring` 挡不住同一用户态进程读凭据（macOS Keychain 的
   ACL 默认允许同一签名的应用读取；Windows Credential Manager 同名进程可读）。
   它真正多出来的是"库被拷走时私钥不在里面"，而库同时含全部消息明文。
2. **跨平台实现差异大**：macOS Keychain 条目与签名/更新绑定（重签名会触发 ACL 提示），
   Windows Credential Manager 有单条 blob 上限，Linux 依赖 Secret Service
   （无桌面环境的机器上不可用），移动端又是 Android Keystore / iOS Keychain 另一套。
3. **迁移与回滚风险**：旧库兼容、双读顺序、失败回退、回滚后旧版本仍要能读 —— 一次
   身份迁移做错的代价是"好友看到的指纹变了/旧消息解不开"，远高于它挡住的那一类攻击。
4. **供应链**：新增依赖即新增被审计面（本仓刚把 `cargo deny` 纳入门禁）。

**何时改主意**（任一成立就重新评估）

- 威胁模型升级为"同用户态进程也不可读"（例如产品要面向共享工作站/网吧场景）；
- 产品要求"导出/备份数据库不得包含私钥"；
- 平台提供了**无需每次确认**且跨桌面/移动一致的系统凭据 API。

**将来若做，迁移路径（写在这里，避免下次从零设计）**

1. 新增 `keyring` 依赖，先只写不读；
2. 启动时：DB 有 base64、系统钥匙串无值 ⇒ 写入钥匙串，**DB 值保留**并记 marker
   （回滚兼容：旧版本仍读 DB）；
3. 读取顺序：钥匙串 → DB（钥匙串不可用时回退，启动不能失败）；
4. 观察一个版本后再决定是否删除 DB 值；删除也必须保留"钥匙串不可用"的回退路径；
5. 判据：旧库升级后 `device_id`/公钥/好友关系不变、消息可读；钥匙串不可用时仍能启动；
   回滚到旧版本后仍能启动。真机矩阵：macOS、Windows、Linux（有/无 Secret Service）。

## 六、本决策的验证方式

- 机器判据（已有）：`db::migration_tests::init_tightens_database_sidecars_and_backup_to_owner_only`
  与 `logging` 的权限用例 —— 库/侧车/备份 `0600`、日志目录 `0700`、日志文件 `0600`。
- 手工复核：`ls -l` 看 `gosslan.db` 与 `-wal` 的 mode；`stat -f "%p"`（macOS）。
- 本文件即"威胁模型已写明"的交付物；未运行的验证：无（不涉及代码改动）。
