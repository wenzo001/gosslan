## 一、方法：六项标准 + 两道门

六项逐格记：可执行 / 可打断 / 可恢复 / 用户可感知 / 可验证 / **可诊断可追溯**。每格取 `PASS / PARTIAL / FAIL / UNVERIFIED / BLOCKED / 不适用(理由)`，**不适用不等于通过，UNVERIFIED 与 BLOCKED 不计入通过率**，每个结论必须挂证据指针。

错误路径按链审，不按点审：**产生 → 分类与记录 → 安全处理 → 用户反馈 → 诊断查询 → 恢复或安全终止 → 结果留痕**（矩阵第四节就是这张表）。禁止静默吞掉影响业务结果的错误、把未知误报成成功或失败、只靠 Toast 当记录、让重试覆盖原始失败证据。

每个操作要回答：谁创建、谁执行、**谁拥有取消权、谁决定最终状态**、何时真正开始、何时算业务完成、超时/取消/失败/部分成功/重复/迟到怎么处理、退出与崩溃后怎么恢复或终止、前端↔内存↔数据库↔对端↔磁盘怎么对账、用户怎么看进度与原因与历史。

**立案要过两道门**：门一「断链证明」要先把链上所有兜底逐一证伪（启动四条对账、带结论的事件类、去抖 flush 出口、`-lie` 反向轮次、后端二次校验）；门二「修改必要性」要答收益落在哪档优先级、感知频率、爆炸半径、会不会引入新风险，结论三选一 **修 / 不修（写理由）/ 换更小的修法**。「不修」是一等结论。

## 五、大白话：哪些地方做的有问题，我要怎么改

**先说结论性的好话，免得听着像挑刺**：这个仓的崩溃恢复是全仓做得最好的一族——启动时四条对账各自带具名错误码，谁改了什么状态、改了几条、失败了怎么喊，全都有记录。取消的消息语义也做得细：取消和送达抢，谁赢由数据库说了算，抢输了界面会说「已经传完」而不是骗你说「已取消」，而且这些文案有六条真测试钉着。**我原本以为的三个大坑，查完发现是作者故意这么设计的，理由就写在注释里。**

真正有问题的是四件事，都**不坏在现在，坏在下次改动**：

**1）「安装中途不许取消」这道门，是纸糊的。**
更新程序在安装的时候不能再取消——因为字节已经交给安装器了，这时候取消会留下装了一半的脏现场。仓里专门写了注释说这条有「两道保证」。我去数这两道：第一道是界面上不显示取消按钮，它比的是 `"installing"` 这个词；第二道是后端直接拒绝，比的也是这个词。
问题是这个词在代码里被手抄了 **12 遍**（后端 2 遍、前端 10 遍），中间没有任何一个共同的定义把它们绑在一起，而且跨进程传的时候类型是**一句字符串**，不是有限的几种取值。
最要命的是那条 supposedly「保证」的测试：它做的事情是把源码读进来，检查「`installing` 和『无法取消』这两个字符串还在不在函数体里」。**它一次都没有真的调用过取消这个操作。** 所以哪天有人把写入状态的那行改成别的词，两道门会同时关不上——界面上按钮出来了、后端也不拦了——而那条测试照样是绿的。
怎么改（按便宜排，都不动状态机）：后端两处引用同一个常量，改错立刻编译不过，这是最省的一刀；再补一条**真的调一次**取消、断言它返回错误的测试。前后端之间那个取值集合要收，就照仓里已有的那条「Rust 字段和 TS interface 必须逐字对应」的判据扩过去，**不要新写脚本**。

**2）改设置如果没存进去，你既不会看到提示，也查不到任何记录。**
主题、语言、聊天样式、**允许中继、绑定哪张网卡**，这些改完都是靠一条 300 毫秒合并写入的通道落库。这条通道失败的时候是**什么都不做的**——不弹提示、不写日志。
我本来打算撤这条，因为它有关窗前的兜底（关窗前和切到后台时补写一次，合并写入的语义也确实有测试钉着）。但按你新加的第六项「可诊断可追溯」走了一遍链，结论是：这笔错误在**记录这一环就是空的**。日志里没有，导出的诊断包里自然也没有。
所以真实的场景是：你明确选了允许中继、或者手动绑了某张网卡，那一次写库没成功，界面还是你选的样子，重启之后回到旧值——**而且事后查不到为什么**。
怎么改：先在 `catch` 里补一条记录（是哪一项设置、错在哪），**这一步零界面变化**；要不要让用户看见，建议不是每次失败弹一条（拖动取色器的时候那会刷屏，仓里就为这事加过去抖），而是置一个标志，让设置页顶部一条「未保存」状态行说话。另外那条关窗兜底在 Tauri 真窗口销毁下到底跑不跑，现在没人测过——先用探针量一次，量出来不跑就改成显式的落库出口，别靠窗口事件。

**3）「点了取消」这件事，除了群消息，都没留下任何痕迹。**
群消息取消会写一行带编号的记录（谁的消息、几个成员已收到、几个还没）。1:1 消息取消、文件取消、内容取消、更新取消，**结局一行都不写**，连「用户点了取消但消息其实已经送达了」这种明显是竞态的结局也不写。数据库层同样是静默返回。
这是同一个函数里的不对称：群的那条有，1:1 的那条没有——如果是有意的，按这个仓的习惯会写一句为什么，但它没有。
后果不是数据坏，是**事后查不动**：用户说「我明明点了取消，对方还是收到了」，你手上没有任何东西能证明当时是竞态、是没点到、还是成功了但对方已读。
怎么改：只在**竞态和被拒**这两类结局补一行带编号的记录，别追求每次取消都写一行（按你的口径，正常成功的取消可以不记，也不要为了「完备」把日志灌满）。补两处就够，都不改契约。

**4）前端界面「点了到底有没有反应」，机器完全不知道。**
132 个前端测试文件里，**69 个是在读源码文本找关键词**——它们能守住「这个名字还在、这条 import 还在」，守不住「按下去发生了什么」。全仓没有一次真的把组件挂载起来点一下（没有 jsdom、没有 vitest、没有 @vue/test-utils，代码里 `mount()` 零命中）。所以按钮接错线、状态没上屏、点了没反应这类事，改坏了没有任何东西会红。
怎么改：**不要引一套测试框架**（仓里已经明确写了探针故意不引 playwright，加了就是为了让测试而改动项目外的东西）。走现成那条路：`scripts/check-ui-runtime.mjs` 已经在真浏览器里跑、能读真实 DOM、已经有 67 段，只是**没人把 B1 这几个动作补成段**。一段一段加，每段照仓里规矩配一发反向对照（改坏必须红）。

**还有三件「看着像问题、其实不用动」的**，写出来是为了别让下一个接手的人重新发现一遍：更新器不持久化（重启重走一次只要一条命令，给它建台账要新加一张表并重对一遍终态不变量，不值）；命令层不属于任何业务域（登记过的装配层豁免，Phase 7 拆，硬塞进去会让正当引用全变违规、第一天全红然后被绕过）；协议里没有发送方放弃帧、靠每小时清扫（作者写明治的是永久泄漏不是界面转圈，加帧要先定旧版本收到不认识帧的口径，那是协议决策）。
