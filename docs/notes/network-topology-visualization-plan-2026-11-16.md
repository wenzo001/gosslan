## 结论

现有拓扑页使用“本机在中心、节点按圈层和中继类型展开”的稳定放射布局。它在实现上有合理的稳定性考虑：布局确定、已有节点坐标保留、刷新不轻易夺走用户相机；但视觉隐喻仍接近“中心设备带一圈节点，再由中继中心带下一圈节点”。这与产品希望表达的去中心化 Mesh 容易冲突。

需要注意，当前后端可供该页面使用的数据主要是“本机到每个 Peer 的最佳路径”和好友会话的 hop 数；它没有提供任意两个远端 Peer 之间的连接边。`hop > 0` 也没有给出经过哪些中继节点。因此，单纯把放射布局换成力导向图、增加节点之间的连线，仍然不能真实展示全网网状关系。方案分两层：先把现有数据明确表达成“本机观察到的网络邻域”，避免中心化误读；再补充有来源、有时效的路径关系数据，满足完整 Mesh 图的条件后展示全网拓扑。

## 产品表达原则

1. **图的主语是“本机正在观察到什么”。** 本机可以作为视图焦点，但不得表现为网络的权威根节点或中心服务。
2. **节点与边分开。** 节点代表稳定设备身份；边代表有来源、有时间的路径关系。颜色、图标或节点分组不能替代边的证据。
3. **当前路径与可达关系分开。** “本机当前选用 LAN 路径”不等于“这两个节点之间只有 LAN 一条路径”，也不等于“全网通过本机路由”。
4. **Relay、Routed 和 Mesh Hop 分开。** Routed 是对端真实 IP 可达；Relay 是经公网中转服务器建立的密封电路；Mesh Hop 是经过多个 Gosslan 节点转发。它们不是同一种中继。
5. **未知状态显式保留。** 没有链路、未发现、数据陈旧、部分关系未知，都不能折叠成“离线”或“无连接”。
6. **布局稳定优先于动画。** 拓扑变化时尽量保留节点位置与用户视角；只在用户请求时整理布局。

## 推荐的信息架构

### A. 默认视图：我的网络邻域

第一阶段不称为“全局网络图”，可使用“我的网络”或“本机网络邻域”。保留本机作为视觉焦点，但通过副标题说明“从这台设备观察”，并将其图形标识为“本机”，而不是 Hub/服务器。

- 直接链路 Peer 显示为邻接设备；每个节点边上明确标记当前路径类型：LAN、Routed、Bluetooth 或 Relay。
- hop 大于 0 的 Peer 以“经 Mesh 可达 · N 跳”状态展示；在没有中间设备身份时，不画虚构的中间节点和边。
- 不把 relay server 画成 Gosslan 节点。若保留路径摘要，可用图外分组/摘要卡显示“公网中转路径 N 条”，点开解释这是路径类型，不是本机控制中心。
- 将在线好友、在线非好友、离线好友、已发现未建链、关系未知/数据过期做成不同的视觉状态；离线好友可留在图旁的列表或筛选结果中，不能把它们画成仍在线的连线。
- 图旁或底部提供紧凑图例和关系说明；点击节点仍打开详情，详情显示“本机当前路径”和数据更新时间。

### B. 目标视图：有证据的 Mesh 关系图

当系统能提供远端节点之间的路径证据后，再启用“Mesh 关系”视图：

- 节点按稳定身份显示；不设中心服务节点。
- 用稀疏、低交叉、稳定的力导向/约束布局初始化；稳定后冻结坐标，后续只做局部调整。用户可拖动、固定和复位节点。
- 边按关系数据展示，并可区分“当前直连”“经过中继可达”“已知但非当前选路”“路径状态陈旧”。
- 本机是视图焦点而非拓扑根；用户切换焦点时图只改变观察视角，不更改网络关系。
- 不为了“看起来像网状”而自动连接相邻节点、补三角形或添加装饰边。

## 图形语法

| 图元 | 必须表达的语义 | 禁止暗示 |
|---|---|---|
| 设备节点 | 一个稳定 device identity；好友/非好友、在线/离线是节点状态 | 节点相邻不代表网络相连 |
| 实线边 | 当前观测到的直接传输路径，或数据契约明确标注的连接 | 不得将推测的可达性画成直连 |
| 虚线边 | 已知的逻辑可达/中继路径，需标明 hop 数或 relay 类型 | 不能在没有路径证据时用虚线作装饰 |
| 边标签 | LAN / Routed / Bluetooth / Relay / Mesh N 跳；多路径时标当前首选路径 | 不能把 Relay 显示成对端 IP，也不能把 Routed 标成 Relay |
| 陈旧状态 | 关系曾观测到，但更新时间已超过契约阈值 | 不得显示为实时在线 |
| 未知状态 | 本地没有关系证据或后端未提供 | 不得当成离线、故障或零跳 |

关系数据将来建议统一包含：`source_device_id`、`target_device_id`、`relation_kind`、`path_kind`、`hop_count`、`selected`、`health`、`observed_at`、`expires_at`、`provenance`。边必须由后端或明确的受信观察源产生；前端只负责布局、过滤、呈现和解释。具体 IPC 名称和序列化格式应在实现阶段结合现有 Rust/TypeScript 契约与协议不变量评审后定稿，本方案不直接规定 wire protocol。

## 布局与交互要求

### 布局

- 淘汰“按两圈/扇区展示拓扑层级”的主隐喻，尤其不要让合成 relay/mesh hub 成为视觉中心。
- 在当前数据阶段，用“自中心邻域图 + 清晰路径标签 + 可筛选设备列表”作为诚实视图；它表达“本机观察”，不假装全网视图。
- 获取全网边数据后，采用稳定的分布式网络布局：节点初始位置由拓扑签名/稳定哈希生成；首次布局后缓存用户位置；网络增量只移动新节点或局部冲突节点。
- 禁止 15 秒轮询时重跑全图模拟或按节点数量自动缩放，避免用户正在拖拽/查看详情时被抢相机。
- 自动适配只在首次打开、用户点“适应画布”或明确切换过滤范围时发生。提供“重置布局”和“聚焦本机”按钮。
- 桌面适合图与详情并列；移动端默认显示可操作的大图区域，详情改为底部抽屉/面板，保留图例入口和一键切换列表。

### 交互

- 节点选中后显示名称、好友身份、在线状态、当前选路、hop、RTT（若可用）和最后更新时间；只有确实具备对应信息时才显示地址。
- 对本机可执行的动作沿用现有动作：好友可打开聊天；非好友显示加好友/处理申请。
- 图例项可开关；筛选好友/全部节点/离线好友/路径类型不应改变数据本身。
- 提供图/列表双视图，列表作为小屏、键盘和读屏用户的等价入口；焦点移动要在节点与详情之间可预期。
- 对高密度网络按簇折叠只允许基于真实关系分组（例如共同的可验证路径关系或用户指定标签），不能依据几何相近自动制造簇语义。

## 状态与边界兜底

| 状态 | 页面应该表达什么 | 可执行动作 |
|---|---|---|
| 初次加载 | 骨架或 Spinner；说明正在获取本机网络视图 | 可关闭页面；避免空白画布 |
| 正常有节点 | 当前可观察节点与路径；注明数据时间 | 刷新、筛选、开详情 |
| 无 Peer | 明确“当前没有在线邻居”，与加载/失败区分 | 重试、去添加好友或检查网络设置 |
| 好友离线 | 节点/列表离线样式，不画在线路径 | 加入离线好友显示筛选 |
| 部分链路数据失败 | 保留成功取得的数据，并指出缺失维度 | 单独重试失败的来源 |
| 完全加载失败 | 通过 StateBlock 展示错误，保留上次成功视图并标记可能过期 | 重试、查看网络诊断 |
| 轮询刷新中 | 小型非阻断状态提示；不清空现有拓扑、不重排 | 用户可继续操作 |
| 关系已过期 | 边淡化/标记陈旧，显示最后观测时间 | 手动刷新 |
| 用户拖动/缩放中 | 相机归用户所有 | 只有用户命令才复位/适配 |
| 超多节点 | 有界渲染、聚合摘要和列表分页/虚拟化 | 搜索、筛选、聚焦 |

任何缓存的旧视图均须带数据时间和陈旧状态；不能用“旧数据仍有节点”掩盖后端刷新失败。刷新竞态遵循已有 stale guard/single-flight 等共用模式，错误不得被当作空数组覆盖当前视图。

## 可执行落地计划

### 阶段 0：产品语义与证据契约（先做）

1. 产品确认页面名称是否从“网络拓扑”改为“我的网络”，并确定是否分“我的邻域 / Mesh 关系”两个视图。
2. 明确每一种线的来源和含义，逐条对照当前 `Peer.link`、`LinkState.path/hop`、`Peer.connections`，登记当前能提供和不能提供的字段。
3. 确定全局拓扑是否属于本产品目标：若要求展示全网远端边，则先设计并评审后端关系数据的权限、来源、过期、体积和隐私边界；若当前只支持本机视角，则产品文案始终称为“本机观察”。

**交付物：** 一页语义表、现有字段覆盖表、明确的“不可推断关系”清单。

### 阶段 1：不扩协议的视图改造

1. 去掉“合成 Hub 是真实节点”的视觉表达，hub 数据改为路径摘要/分组语义；在 UI 中明确这不是中继设备清单。
2. 减弱中心辐射的树状观感：本机作为被选中的观察端点放在侧边/底部锚点或视觉焦点位，直接节点在周围分布；图中仍只画本机到已知 Peer 的实际关系。
3. 给每条关系显示准确的路径标签，区分 Relay、Routed、Mesh Hop，并给多跳路径提示“中间节点当前不可见”。
4. 增加同源列表视图、筛选、刷新状态和最后更新时间；完善陈旧、部分失败、无结果状态。
5. 保留稳定坐标、用户相机归属、首帧懒加载和响应式尺寸规则。

**交付物：** 桌面与移动交互稿/状态表；基于真实现有数据的可评审拓扑原型。

### 阶段 2：稳定的非中心布局

1. 选定布局策略：以轻量确定性约束图布局为优先，不用无边依据的纯视觉 force simulation。
2. 通过稳定 seed 给新节点位置，节点稳定后固定；只对新增/移除邻居做局部解碰撞。
3. 保存用户拖拽位置（先决定本地偏好存储，避免进入网络协议），提供恢复默认布局。
4. 评估 10、50、200、500 节点的布局时间、帧率和画布交互；若规模较小时仍能用当前依赖实现，优先复用已有图形依赖，避免再造力学算法。

**交付物：** 布局决策记录、性能预算、不同规模原型。

### 阶段 3：真实全网关系（可选，取决于产品确认）

1. 后端提供有来源的 peer-peer 关系/转发路径，明确哪些数据是本机事实、哪些是远端通告、哪些只是推测。
2. 为关系设置 TTL、版本和最大数量；处理远端身份验证、重复、陈旧、断链和环路。
3. UI 只呈现通过校验且仍有效的关系；未经验证的远端通告必须单独标注，不能与本机连接事实同样式。
4. 逐项评审隐私影响：设备标识、邻居集合和网络结构可能揭示用户关系；默认最小披露，未明确授权前不向其他 Peer 广播整份拓扑。

**交付物：** Rust/TypeScript 接口契约、协议兼容方案、隐私与威胁评审、迁移/降级策略、端到端验收计划。

## 风险与取舍

| 风险 | 影响 | 缓解方式 |
|---|---|---|
| 没有远端 peer-peer 边 | 全网看起来仍不是完整 Mesh | 诚实地以“本机邻域”命名；全局视图等待真实数据契约 |
| 合成中继节点被误认为实体 | 用户误解 Relay/多跳关系 | 将其改成路径摘要，不放进设备节点图例 |
| 力导向布局持续漂移 | 视图难读、刷新抢操作 | 确定性初始化、稳定后冻结、局部增量布局、用户可固定节点 |
| 过期关系仍显示在线 | 网络状态失真 | edge freshness、明确 last observed、陈旧状态优先于在线表现 |
| 全局拓扑广播带来隐私泄露 | 暴露好友/邻居结构 | 默认只用本机观察数据；全局关系必须有授权/TTL/最小化设计 |
| 图形节点增多导致操作困难 | 小屏和无障碍用户无法使用 | 列表等价视图、键盘焦点、读屏名称、聚合和检索 |

## 验收清单

- [ ] 每条边都能追溯到明确字段、观测者与时间；没有装饰性/推断性连线。
