# Webhook 通知机器人接入指南（给发送方）

> **2026-11-17 v7 简化（当前协议）**：认证 token 在 URL、GET/POST/PUT 都能发，
> 一条 curl 完成；服务端单进程复用 59994。
> **完整接入说明见 `gosslan-relay-server/README-v7-notify.md`**，最快示例：
>
> ```bash
> curl "http://服务器:59994/publish/<send_token>?text=构建完成&title=CI"
> ```
>
> 旧 v6 的 `/v1/hooks/...` + Authorization 头协议**已删除**，下面 v6 段落仅供历史参考。

> 读者：**要往 Gosslan 发通知的外部系统**（CI、监控、构建脚本、工单系统……）。
> 你不需要装 Gosslan、不需要懂它的协议 —— 只要会发一个 HTTP POST。
>
> 一句话：**Gosslan 里的机器人就像一个接收器**。对方（你）拿到一个专属网址和一把密钥，
> 往那个网址 POST 一段文字，这条消息就会出现在对方的会话（个人机器人）或群里
> （群机器人）。
>
> 完整接口契约见 `gosslan-relay-server/webhook-api.md`；本文只讲「怎么发」。

## 1. 你要先拿到两样东西

这两样由 **Gosslan 用户**在创建机器人时生成，一次性交给你：

| 东西 | 长什么样 | 用途 |
|---|---|---|
| **Endpoint** | `https://<服务地址>/v1/hooks/<bot_id>/messages` | 往这里发 POST |
| **Send token** | 一长串随机字符串（base64url） | 放在 `Authorization` 头里证明「我有资格给这个机器人发」 |

⚠️ **send token 只在创建那一刻显示一次**，丢了找不回来 —— 让用户删掉旧机器人重建一个
（旧的 hook 会立即失效）。**不要把 token 写进代码仓库或日志**。

一个机器人只服务一个目标：要么是创建者的个人会话，要么是某一个群。发给 A 机器人的
token 不能给 B 机器人用。

## 2. 发一条最简单的通知

```bash
curl -X POST 'https://hooks.example.com/v1/hooks/bot_7f3a9c.../messages' \
  -H 'Authorization: Bearer <你的 send token>' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: build-20261116-001' \
  -d '{"text":"构建完成：main 分支已通过全部测试"}'
```

成功返回 `202`，body 里有一个 `event_id`（这次投递的编号，可拿去查状态）。

**必填**只有 `text`。`Authorization` 头与 `Idempotency-Key`（强烈建议）见下文。

## 3. 正文：纯文本或 Markdown

```json
{ "text": "## 部署完成\n- 版本 **5.42.0**\n- [查看日志](https://example.com/log)", "format": "markdown" }
```

- `format` 缺省 = `text`（纯文本，原样显示）；
- `format: "markdown"` 支持标题 / 列表 / 粗体 / 链接 / 代码块等常见语法；
- ⚠️ **群机器人的 Markdown 按纯文本显示**：群消息走既有群聊线格式（协议冻结），
  不能带结构化格式标记，所以群里看到的是带 `【机器人名】` 前缀的字面文本。
  **要完整 Markdown 渲染，请用个人机器人**（消息进会话）。这一点对发送方透明：
  你照常发 markdown 即可，只是群侧不渲染；
- **不支持 HTML** —— 里面的 `<script>` 等标签会被当纯文本处理并消毒，不会执行；
- **长度上限 8192 UTF-8 字节**（中文一个字约 3 字节），超长按字节**截断**，不报错、
  不整条丢弃。Markdown 与纯文本同一把尺子；
- ⚠️ **当前版本不支持图片通知**：即使请求带了 `images`，客户端也不会下载或显示图片，
  只会在正文后附一句「这条通知附带 N 张图片，当前版本不支持图片通知」。
  请**只用文字 / Markdown** 传达信息；不要把关键内容放在图片里。

## 4. 幂等：同一条通知别发两遍

网络抖动时你可能会重试。带上 **`Idempotency-Key`**（你自己的唯一编号，比如构建号 /
工单号），服务端保证同一个 key 只入队一次：

```bash
-H 'Idempotency-Key: deploy-2026-11-16-run-42'
```

同一个机器人、同一个 key 的重复请求会返回第一次的结果，不会让对方收到两条。
key 建议按「事件 + 唯一实例」拼，别用固定字符串（那会让后续所有通知都被当成重复）。

## 5. 查这一条到哪了（可选）

创建时若拿到了查询用的凭证，可以用返回的 `event_id` 查状态：

```bash
GET /v1/hooks/<bot_id>/messages/<event_id>
```

状态：`queued`（已入队，等设备来取）→ `leased`（某台设备正在处理）→
`accepted_by_gateway`（对方已收到）。异常会走到 `retry` / `failed` / `expired`。

⚠️ 只有**一台**在线设备会去取件（网关），其它设备不连这个服务 —— 所以 `queued`
不代表对方没看到，只代表还没轮到取。

## 6. 常见错误

| 状态码 | 含义 | 怎么办 |
|---|---|---|
| `401` | token 错了 / 机器人已撤销 | 确认 token 没写错；若对方删了机器人，让它重建一个 |
| `400` | 请求格式不对（比如没有 `text`） | 检查 body 是不是合法 JSON |
| `403` | 机器人被暂停了 | 让对方在机器人详情里恢复 |
| `413` | 请求体太大（默认 24 MiB） | 正文超长会被截断而不是报 413；这个通常是图片过大 |
| `429` | 发太快了（每个机器人 60 次/分钟） | 退避重试，别死循环 |
| `503` | 服务不可写 / 未就绪 | 稍后重试；看 `/healthz` 的 `storage_writable` |

**别做的事**：不要把 token 放 URL 查询参数（`?token=…` 会进访问日志）；不要用一个机器人
群发到多个目标（要不同目标就建不同机器人）；不要在正文里塞密钥/密码（服务能看到明文，
且会落盘）。

## 7. 接入检查清单

- [ ] 从 Gosslan 用户那里拿到 endpoint + send token（并确认保存好了 token）
- [ ] 用上面的 curl 发一条测试消息，对方能在会话/群里看到
- [ ] 加上 `Idempotency-Key`，确认重复发不会出两条
- [ ] 长文本走 `format: "markdown"`，确认换行与链接显示正常；**不要用图片传关键信息**
- [ ] 给 401 / 429 / 503 加了退避重试，不会对服务端重试轰炸
- [ ] token 存在密钥管理里，没进代码仓库、没进日志

## 8. 边界与信任（重要）

- 这个服务是**自托管**的，运营者能看到消息**明文**并落盘 —— **不是端到端加密**。
  别用它传敏感信息。
- 你的 send token **只能提交消息 + 查状态**：不能拉取历史、不能改机器人配置、
  不能读聊天记录。
- 机器人是**单向**的：你只能往里发，不能从里面读对方的回复。要双向请用 Gosslan 的好友/群。
- 每个 Gosslan 用户各自创建自己的机器人、各自保管自己的密钥 —— 不存在全局共享的机器人。
