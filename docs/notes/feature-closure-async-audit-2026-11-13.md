# 功能闭环与异步任务状态审计

审计日期：2026-11-13  
范围：前端 `src/` 与 Tauri/Rust 后端 `src-tauri/src/` 中可见的主要产品功能、状态迁移和后台异步作业。  
边界：只读源码审阅；未修改程序代码，未运行测试、lint、类型检查、构建或端到端流程。结论说明源码中可见的设计和风险，不代表运行时完整性证明。

## 审计结论

项目并非普遍缺少状态闭环。消息发送、文件传输、任务中心、更新器、群历史同步、好友申请等主要链路已有明确状态、进度或失败反馈；部分操作具备乐观投影、失败回滚、重试、取消和持久化恢复。

但目前不能据源码静态审阅证明“所有功能、所有状态和所有边界都已兜底”。功能间的生命周期承诺不统一：有的后台任务可跨重启恢复，有的进程重启后终止；有的错误可在任务中心重试，有的只通过 toast/气泡反馈；也有少数乐观回滚和台账收尾需要并发/错误注入验证。产品上应建立按功能逐项维护的异步能力清单，避免要求所有操作都支持乐观更新、取消或撤回。

### 本轮确认的主要改进项

1. **P1 — 内容拉取取消后的多条台账收尾可能短路。** `cancel_content_fetch` 先停止接收器，再用 `Iterator::all` 逐条写失败/取消台账（`src-tauri/src/commands/files.rs:1212-1238`）。Rust 的 `all` 在首个 `Err` 后停止遍历；其余记录可能未尝试收尾，造成“接收已停，部分记录仍显示活动”的不一致。应逐条尝试、汇总写入结果，并确保 UI 可重查和区分部分收尾失败。
2. **P2 — 多处乐观失败回滚整份旧快照，存在并发覆盖风险。** 群信息/成员（`src/stores/chat/groups.ts:62-185`）、删除好友（`src/stores/chat/contacts.ts:150-170`）、删除会话/置顶（`src/stores/chat/conversations.ts:753-797`）及批量删消息（`src/stores/chat/messaging.ts:688-703`）可见捕获旧数组后整体恢复的模式。如果同一集合上的另一项操作先成功、后一个操作失败回滚，旧快照可能覆盖先成功的变更。需要先核对调用 UI 是否阻止同对象并发，再采用按实体/操作局部逆操作回滚或同实体串行化。
3. **P2 — 部分状态读取失败可能保留旧值但缺少“数据已过期”提示。** 群投递摘要刷新失败时保留现有快照（`src/stores/chat/conversations.ts:640-651`）；这避免了把读失败伪装成空数据，但应确认用户能识别旧数据，并能主动刷新。建议补充独立 stale/error 标记，而不是清空正确的旧值。
4. **P2 — 后台任务跨重启语义尚未统一。** 任务中心只收录部分持久后台任务；源码说明更新下载状态保存在内存中，重启后任务行消失，Todo 图片和共享目录下载不在统一任务台账中（`src/utils/taskCenter.ts:18-31`）。这是生命周期契约/入口覆盖问题，不等于相关功能完全不可用。需要逐项决定“重启恢复、重启后终止、重新开始”，并对不可恢复工作提供明确说明。
5. **P3 — 群历史同步启动等待期缺少按群即时 pending 状态。** `syncGroupHistoryNow` 等待 IPC 返回后才 toast，运行横幅又依赖首个进度事件（`src/stores/chat/conversations.ts:74-97`）。虽然代码已补 started 等返回后的反馈，任务也有运行/失败/取消阶段，但连续点击期间尚未看到 store 层按群记录启动中的请求。建议评估按钮忙状态、同群去重和启动超时反馈。
6. **P3 — 群文件进度/气泡的注释可能已过时。** `src/stores/chat/media.ts:72-73` 写明群文件气泡/进度留待后续阶段；当前 `MessageFileBubble.vue` 与 `GroupFilesPanel.vue` 已能展示群文件状态/进度并提供操作。建议核对实际覆盖后更新注释，避免后来维护者误判功能缺失。

以上严重度是审计建议顺序，不代表每项已由运行时复现。P1 项有控制流短路的直接源码证据；P2 并发覆盖项的实际暴露取决于调用层是否已禁止同实体并发。

## 按功能的状态与操作能力矩阵

| 功能域 | 可见状态/真值来源 | 乐观更新与进度 | 取消、撤回、重试、恢复 | 审计判断 |
|---|---|---|---|---|
| 普通消息发送 | `sending` 后替换真实记录；Ack 可先于 invoke 返回；失败保留为 `failed` | 文本消息乐观上屏；Ack/迟到失败有守卫 | 失败可重发；取消发送与撤回是不同协议动作；发送 invoke 本身未见通用 Abort API | 核心闭环较完整；不要把未确认发送伪装成远端成功 |
| 消息撤回/反应/渲染 | 撤回依赖可靠 outbox 与对端事实；反应按服务端结果入账 | 撤回/反应避免伪造远端成功；部分操作有任务中心临时行 | 撤回不是本地 undo；失败后按台账重试，具体边界由协议判定 | 语义保守且合理；不同操作不可统一强加 optimistic |
| 单聊文件/图片传输 | 持久台账、字节进度、停滞/恢复、完成/失败事件 | 发送可先插本地行，失败清理幽灵投影；进度丢行会安排快照修复 | 传输取消、失败重试/续传、内容重新获取均有专用路径 | 较完整；需验证事件丢失、进程重启和取消后台账收敛 |
| 群文件 | 后端群文件/成员投递台账，群文件面板和消息气泡显示状态 | 群文件由独立发送链路创建；成员进度聚合并有失败事件 | 取消、重新获取、断点/离线补投按专用规则处理 | 能力存在；关注多接收人部分失败与取消后的部分提交说明 |
| 群历史同步 | 后台进度事件，UI 横幅；failed/cancelled 会结束提示 | 不是乐观内容写入；已接收页面保留 | 协作式取消（页/批次边界停止）；失败后用户可重新发起 | 主流程有闭环；启动等待期 pending、停止后恢复方式可更清楚 |
| 好友申请/成员管理 | 申请状态及后端刷新；操作失败恢复 UI | 好友申请撤回、接受/拒绝、群成员/管理员有乐观更新 | 申请可撤回；好友删除是确认后不可逆；成员动作按后端权限处理 | 设计总体合理；快照整体回滚需审查并发保护 |
| 任务中心 | 聚合多份真实任务台账为 queued/running/blocked 等视图 | 展示进度、失败原因、等待/阻塞信息；读失败保留可区分的旧数据 | 按任务能力提供取消/重发；只列未完成，终态由其他界面反馈 | 可视化较好，但不是所有后台工作的统一入口，也不是操作历史 |
| 桌面/Android 更新器 | 显式阶段、下载量/总量、错误与安装阶段 | 下载进度条和状态文案 | 下载可取消/失败重试；安装开始后不可取消 | 安全边界明确；需确保“不可取消”阶段的告知与退出恢复预期清楚 |
| 搜索、设置及只读面板 | 多数可从组件/Query 状态看到 loading/error/retry | 不应做写入式 optimistic | 适合重试查询，不适用撤回；部分面板以重新打开刷新 | 逐面板验收错误、旧数据陈旧提示和无结果/无权限边界，不能套用写操作控制 |

### 术语和原则

- **乐观更新**只适用于本地可逆、且能明确回滚或由服务端确认的动作。跨端发送成功、付款/安装、不可逆删除不能为“即时”而提前展示成已成功。
- **取消**表示请求停止尚未完成的工作；**撤回**表示改变已发送给对方的事实；**撤销/undo**表示在约定窗口内恢复本地变更。三者不能共用一个状态或按钮语义。
- **恢复**至少分为页面重新查询、失败任务重试、断点续传和进程重启恢复。报告或 UI 应明确是哪一种，不能只写“支持恢复”。
- **进度可见**应同时说明口径：已写本地、已发送到链路、对端已接收或完成。非已知总量时显示不确定进度，不应伪造百分比。

## 改进方案与实施计划

### 阶段一：建立功能级闭环台账

对每个用户可发起的长流程记录以下字段：

| 字段 | 需要明确的问题 |
|---|---|
| 状态机 | 初始、排队、运行、阻塞、部分成功、成功、失败、取消、超时分别是什么？终态是否可被迟到事件覆盖？ |
| 状态所有者 | 前端投影、Rust 任务、SQLite 台账、对端 ACK 中哪个是真值源？ |
| 用户反馈 | 操作后立即回声在哪里？进度、失败原因、部分成功、陈旧状态在哪里看？ |
| 反向动作 | 是否允许取消/撤回/撤销？取消最迟到哪一阶段？动作完成后是否幂等？ |
| 恢复能力 | 网络恢复、手动重试、窗口关闭、进程重启分别如何处理？是否断点续传？ |
| 边界与资源 | 重试上限/退避、超时、并发、队列上限、磁盘满、权限变化、事件乱序/丢失如何兜底？ |
| 验收证据 | 哪些状态迁移有单测/集成测试/端到端验证？如何验证“删掉保护就会失败”？ |

把“无此能力”作为有效值登记并给出原因，避免把不可逆动作硬做成可撤销。

### 阶段二：收敛已发现的风险

1. 修复/验证 `cancel_content_fetch` 多记录取消收尾：逐行尝试持久化并汇总成功与失败；确保刷新后失败记录可见，不丢失已停止接收这一事实。
2. 对乐观回滚建立并发策略：优先按对象局部应用逆操作；确需整快照恢复时，为同一实体加单飞/串行队列并在 UI 显示 busy。检查所有并发入口后再确定迁移范围。
3. 为保留旧数据的 Query 统一增加 `isStale`/`refreshError` 表示和重试入口，保持“旧值可用但可能过期”与“空列表”可区分。
4. 为按群/按资源启动的长任务提供即时 pending 与重复请求去重；启动失败、超时和后续事件丢失都能收口。
5. 核对群文件代码注释与当前组件能力，更新过期描述。

### 阶段三：异步体验一致性

为每类长任务制定一致但不强求相同 UI 的体验规范：发起后即时反馈、运行期间可观察、错误说清原因和可执行动作、取消说明是“已停止”还是“正在停止”、部分成功给出已完成/未完成范围、不可取消阶段说明原因、重启后策略可预测。

任务中心作为运行中操作的入口可以逐步扩展，但保留适合留在原页面的状态、终态历史和敏感操作；不要把所有异步调用都塞进全局任务列表。

### 阶段四：逐状态验证

实现时分别验证：慢响应、立即拒绝、超时、重复点击、操作并发、窗口切换、事件先于 invoke 返回、事件迟到/丢失、断网重连、磁盘满、权限/会话切换、应用重启、部分批量成功。验证计划应按领域落在现有测试体系中，并为每个终态和逆向转换保留反例自证。

## 最佳实践

1. 先定义状态图和真值源，再实现 UI；一个状态只由一个权威路径决定，避免不同窗口各自猜状态。
2. 异步命令用明确的返回裁决码区分“已受理”“已完成”“已取消”“已过期/不存在”“部分失败”；长作业再用事件或查询持续同步状态。
3. 乐观写入绑定 operation id / generation；回滚只作用于本次改动，不覆盖并发期间的新事实。后端状态优先于晚到的失败结果。
4. 取消采用合作式语义并与数据库终态同事务/可重放；迟到 ACK 只能记录证据，不能无条件复活已取消状态。
5. 将重试设计为有界、可观测、幂等操作；清楚区分自动重试、用户重试和恢复扫描，不用无限重试掩盖永久错误。
6. 所有查询至少能区分初次加载、后台刷新、陈旧数据、错误、空结果和无权限；保留旧数据显示时需同时暴露陈旧/刷新失败状态。
7. 对每个后台任务明确进程生命周期承诺，并在设置页/任务中心/原功能界面放置对应入口；没有取消或撤回是可以接受的，只要原因和边界明确。

## 证据与限制

- 本轮交叉审阅涉及前端 store/composable/component、任务中心和更新器，以及 Rust 命令、传输、内容台账和 worker supervisor。
- 代表性源码证据：`src/stores/chat/messaging.ts:341-463`、`src/stores/chat/media.ts:28-73,166-226`、`src/stores/chat/contacts.ts:114-145`、`src/stores/chat/conversations.ts:74-118,841-885`、`src/utils/taskCenter.ts:18-105`、`src/components/TaskCenter.vue:149-249`、`src-tauri/src/commands/files.rs:1212-1238`、`src-tauri/src/content/model.rs:157-179`、`src-tauri/src/content/policy.rs:8-91`、`src-tauri/src/commands/updater.rs`、`src-tauri/src/commands/android_updater.rs`、`src-tauri/src/worker_supervisor.rs:19-25,51-117,167-224`。
- 静态审阅无法证明每个页面的所有状态均被覆盖，也未验证网络/平台时序。并发回滚风险需结合对应按钮 busy/禁用和实际多窗口入口复核；取消台账短路需用失败注入确认部分写失败后的 UI 结果。
