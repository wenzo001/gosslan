## 二、记账了什么（查到但本批不改）

1. **运行时裸调 `window.matchMedia`**（`useAppStore.ts` 的 `watchSystemAppearance` 与 `init` 里的
   `NARROW_LAYOUT_QUERY`）。首帧脚本 `theme-boot.js` 有 try/catch 兜底，运行时这两处没有；
   若 `matchMedia` 不存在，`init` 会在创建 mq 时中断。
   **不修的理由**：这是本批之前就有的形状，且 Tauri 三端 WebView（macOS WKWebView / Windows WebView2 /
   Android WebView）都提供 `matchMedia`，触发条件只在测试桩或极端裁剪环境；改成"缺失时按宽度兜底"会把
   `resolveMobileLayout` 的平台优先判据多接一条支路，风险大于收益。记在这里，等真有环境证据再动。
2. **emoji 胶囊与主色气泡的对比度不钉 3:1**（`tokenContrast.ts` 的文字豁免）。
   **理由**：胶囊是有主色底 + 自身前景（`on-primary`）+ 描边的组合控件，套 3:1 会把"同色相淡底"这一档整体判死；
   胶囊内部的文字/图标仍按各自 token 对过阈值。若以后改 `--gosslan-react-bg` 的派生，需人工复核这一处。
3. **`chatStyle.ts` 的气泡文字阈值（4.8，仅 WCAG）与主题求解器（APCA + WCAG 双约束）是两套口径**。
   **理由**：气泡底色由用户自定义聊天背景决定、不参与主题阶梯，强行并到 APCA 会改动用户已选的聊天配色；
   两处都有各自的对比度判据（`tokenContrast.test.ts` / `chatStyle.test.ts`），不属于"悄悄放宽"。
4. **`--gosslan-danger` 对暗面板 2.72**（承白字 4.94）仍是接受项，只写在 `style.css` 注释与
   `docs/design-language/theme-contrast.md §4`，没有机器棘轮。**理由**：这是用户 2026-11-08 拍板保留的
   "深底白字"取值；要加棘轮得先有一个"允许多少"的档位定义，不在本批范围内。

## 三、没发现问题

- **状态单一来源**：主题求解只有 `themePalette.ts::buildThemeTokens` 一处；三份落地副本（运行时
  `applyTheme`、首帧 `theme-boot.js`、`style.css` 静态值）之间的逐值一致性由 `themePalette.test.ts`
  与 `appearance.test.ts` 互锁（含 `compared >= 70` 防空转、`SEED_TOKENS` 条数断言）。
  亮/暗由 `appearance` / `systemDark` / `.dark` 类同源推导；`applyTheme` 每次覆盖全部 token，
  切亮暗没有残留旧内联值。
- **每帧测量**：`MessageReactionBar`（`getBoundingClientRect` 只在 mouseenter/focus 的 `reveal()` 里）、
  `GroupTasksBoard`（菜单/拖拽事件里）、`ToastList`（纯 CSS 变量）都不在渲染路径或 watch 里测量。
- **错误路径降级**：非法色值（`hexToRgb` 递归兜底到默认蓝）、localStorage 抛错、`matchMedia` 抛错或缺失，
  首帧脚本都有 try/catch 且逐例有测试（`appearance.test.ts` 的"一抛全跳"反例 + 正控）。
- **判据是否真空转**：`tokenContrast.test.ts`、`themePalette.test.ts`、`designGuards.test.ts` 的
  源码扫描型判据都带正控或分母下限（`accentSwatches >= 4`、`keys >= 8`、`files >= 180`、matcher 正控）。
- **可读性契约没有被放宽**：`tokenContrast.ts` 本批只新增（react 档 4.5），`KNOWN_SUB_AA` 前后皆空；
  `APCA_LIMITS` 未动且与求解目标双锁；禁用态从"一律 4.5"改成"未禁用档 4.5 / 禁用档按 `ratioUndisabled`"，
  属口径修正（暗色禁用 4.71 本不该红），不是放水。

### 发版时踩到的一格：CHANGELOG 条目归属

首次打 `v5.20.0` 时 Verify 红在「CHANGELOG 结构」，原文：

```
- CHANGELOG.md:17 小节 `## [5.20.0]` 里挂着「稳定性」，而写它的那次提交 f0b348b 自己就是
  把版本提到 5.19.24 的那次 ⇒ 这条属于 5.19.24，不属于 5.20.0
（「界面」「测试」同形）
```

成因：`f0b348bb` 早在 11-08 就把 `package.json` 提到 5.19.24 并写下 `### 稳定性 / 界面 / 测试`
三行，此后所有工作都往同一节里追加、没有再提版；本批按 SemVer 需取 minor（两条 `feat`），
于是我把 `## [5.19.24]` 直接改名成 `## [5.20.0]` —— 这三行标题的字面没有变，判据仍能追到
`f0b348bb`，于是判定"你把 5.19.24 的条目挪到了 5.20.0"。

处置：按本仓既有先例（`docs/archive/notes/changelog-archive.md` 的 5.13.1：「5.13.0 从未发布；
这一版把 5.13.0 的…一起发布」）——**不改判据**，改成 `5.19.24 从未发布` 的引用块说明，
并把本节的小标题换成描述性新标题（`### 启动崩溃归因与运行环境失败` / `### 界面与状态条` /
`### 拖动选色的性能` / `### 判据与测试`），让"谁写的"可证且不跨版。

教训：**给还没有 tag 的版本预先提版 + 预写小节，迟早会和下一次提版撞车。**正确做法是
提版与打 tag 作为同一步；确实要预留，就只在 `[Unreleased]` 里写，不要提前改 `package.json`。
