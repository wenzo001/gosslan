# 群文件台账补账：可行性与那一格启动陷阱（2026-10-16）

**背景**：群收尾那一格曾把三张台账包进一个**忘了 `tx.commit()`** 的事务（`2de9264`，
判据后补在 `lib_file_tests.rs`，见 `docs/archive/audit/ledger-2026-10-16.md` 第 1 节）⇒ 三张一起回滚：文件在盘上、
`group_file_recipients` 不 completed、`file_transfers` 没有 done 行、`content_transfers` 那一行根本没被构造。
后果是那台**不算种子**，别人再也拉不到这个文件；而对账扫描器捞不到它（谓词要求“已有一行且 path IS NULL”）。

> ⚠️ **本文初稿那句「已发版那段时间的机器都没落库」是错的，本轮现读更正**：`git tag --contains 2de9264` 返回空，
> 而 `git ls-remote --tags origin` 现数 68 个 tag、最新 `v4.39.4` ⇒ **没有任何已发布的安装包带着那笔未 commit 的事务**
> （发布流按 tag 触发）。所以「三张一起回滚」只在跑过 `2de9264` 之后那版的机器上成立（本机与内部试用装）；
> 对线上旧版，缺账来自它**前面**那个形状 —— 三处写各吞各的错（两处 `let _ =` + 一处 `.ok()`），某一处写失败时
> 同样停在「文件在盘上、台账不知道」。两种来源不同、**修法同一份**（本作业按「三张台账里有没有任何一张没收口」
> 认候选，不按来源分叉），但别把「线上都坏了」当成既成事实写进任何对外说法。

负责人已拍板：**写一次性补账**。

## 一、为什么不能"扫目录"

群接收落盘名是 `unique_path(downloads, 原始文件名)`（`network/file/group_receive.rs:193`）——
**不含 sha256、不含 transfer_id**，重名还会被加成 `名字 (1).ext`。
所以"扫 downloads 看哪些文件没账"在证据上不成立：文件名对不回群、对不回消息、也对不回内容 id。

## 二、能 soundly 补的那一条路（现读确认信息够）

消息行是**另一条写**（Offer 时 `transport/group_file.rs:103-129` 插的卡片），不在那笔回滚的事务里 ⇒ 绝大多数情况下**消息还在**。
而它带的字段恰好够定死一件事：

| 来源 | 用处 |
|---|---|
| `msg_id = "gfile-{transfer_id}"` | 反推出 `transfer_id`（前缀可判，不会与单聊 `file-` 混） |
| `content.sha256` | **判据本体**：哈希相等才算这份文件 |
| `content.size` / `content.name` | 只用来把候选集缩到"同名同大小"，避免整目录哈希 |
| `conv_id` / `sender_id` | 补 `group_file_recipients` 与 `file_transfers` 需要的群与发起方 |

⇒ 原定步骤是：取 `msg_id LIKE 'gfile-%'` 且缺行的消息 → 在 downloads 里按 name/size 收候选 → **逐个哈希、等于 `content.sha256` 才算命中** → 命中才补三行。

> **实现期更正（现读锁定的形状）**：那笔回滚**没有**碰 `update_message_content` —— 它是事务外的另一句写
> ⇒ 已落盘的那批，卡片 `content` 里**本来就有 `path`**。所以“按 name/size 收候选”那一步不必做（它唯一的价值
> 是把哈希范围缩小）：直接拿 `content.path`，仍然**整份哈希与 `group_files.sha256` 相等才算命中**。
> 少一次目录遍历 = 少一种认错的可能。`content` 里没有 `path` 的（还在收 / 失败 / 从未落盘）没有任何可核对的
> 证据 ⇒ 本轮不碰（与第 5 节同一口径：不许按名字猜）。
**哈希比对是这道补账不会做错的唯一原因**：认不上就不补，绝不靠猜把路径写进台账。
认不上（文件被清理/改名）⇒ 跳过并留痕，**不写半条账**（半条账就是对账扫描器看不见的那种形状）。

## 三、必须避开的陷阱：这活不能跑在迁移里同步做

补账要哈希整份文件，而群文件可以到**数百 MB/GB 级**。本仓的不变量 **INV-P34**
（`docs/protocol-invariants.md`，台账第 13 行）说的就是这件事：
**文件生命周期的 GB 级慢活只许在阻塞线程池里跑**，因为本应用只有一个 tokio runtime，
钉住 worker 多久界面就"点了没窗"多久 —— 这一族已经修过十一家，其中一家正是"设置里点清除数据"那种一次性动作。

所以形态只有两种可选：

| 选项 | 做法 | 代价 |
|---|---|---|
| **A（我推荐）** | 不做成迁移。改成**启动后一次性的后台补账作业**：`spawn_blocking` 逐条处理、每条之间让出、进度与跳过都落日志；只在缺行时才动库 | 要加"跑过没有"的状态位（一个 settings 键），并给这个作业一条**按格点名**的判据 |
| **B** | 做成 DB 迁移（`DB_VERSION` +1） | 迁移在启动路径上同步跑 ⇒ **直接违反 INV-P34**，把"打开应用就卡住/闪退"的入口亲手装回去；只有把哈希完全去掉才安全，而去掉哈希就不再 sound |

⚠️ 这条要写在最前面：**B 看着更省事，但它恰好是这一整个星期在修的那类 bug 的形状**。选 B 之前要有明确理由。

## 四、动手前就要定好的反证（否则判据会空转）

1. **正向**：造一条"消息在、三行缺、盘上有文件且 sha256 对得上"的预置 → 补完必须三行齐、状态 completed/done、path 非空；
2. **反向一**：sha256 对不上（把盘上那份改一个字节）→ **一格都不许写**，并留下那条跳过日志；
3. **反向二**：文件不存在 → 同样不写；
4. **反向三**：已经补过的再跑一次必须**幂等**（不重复插行、不覆盖已前进的状态）——
   这一条要复用 `set_message_status` 那套单调闸口径，别新开一份；
5. **形状**：按 INV-P34 的既有判据补一条"这条新作业里的整文件哈希前面必须有 `spawn_blocking(` 且紧跟 `.await`"，
   并把它的名字**登记进分母判据的名单**（`docs/protocol-invariants.md` 台账第 13 行的那份名字清单，加名字要同批改文档）。

第 2 条是这一格里最值钱的判据：**能拒掉错文件的补账，才配叫补账**；只验"补上了"的用例，等于给一个会写错台账的函数盖章。

## 五、还剩哪一块补不了（如实登记）

消息行也没了的（`insert_message` 失败 + 收尾又回滚）→ 盘上只剩一个文件名，**没有任何证据**能把它对回某个群某条消息。
这一类本轮不处理，也不许"按名字猜"补上；要收口子只能是"新写入已带留痕"（本轮已把五家 `.ok();` 改成留痕）。

**第二类补不了（本轮现读补登记，之前只写了第一类）**：`scope == "todo"` 的群图**按设计根本没有卡片行**
—— Offer 那一段把插气泡包在 `if scope != "todo"` 里（`network/transport/group_file.rs`），待办描述图只走传输管线、
不进聊天时间线。所以本作业的候选来源（`gfile-%` 消息行）**结构性地看不见这一类**，也就数不出它们坏没坏。
4.40.8 那一格如果发生在待办图上，本轮补不了：不是"选择不动"，是**这条路上没有任何证据**。
要收这一类只能另起一格（从 `group_files` 那侧出发按 sha256 找盘上文件），那需要一套新的落盘名口径，
不在本轮范围。已同步写进 CHANGELOG 的"没补的"那一段。

## 六、这一格与闪退那一格无关

补账不碰托盘、不碰 HICON、不碰通知。别把两件事混在一次改里 ——
闪退的读数是 `channel="panic"` 那条日志（见 `windows-crash-capture-2026-10-16.md`）。

## 七、实现记录（2026-10-16 走 A，4.40.9）

落点：`src-tauri/src/network/file/ledger_backfill.rs`（+ 判据册 `ledger_backfill_tests.rs`），
启动那一格在 `lib.rs` 的 setup 里（`.part` 清扫那块之后），候选读的那句 SQL 在 `db/messages.rs::list_gfile_message_rows`。

四件与本文不同 / 需要记下来的事：

1. **判据本体换了来源**：哈希比对仍然算**整份文件**，但比的是 `group_files.sha256`（Offer 写的、
   也不在那笔回滚里），路径取卡片 `content.path`（Done 在**事务外**回填的）⇒ 不做目录遍历（见上面那条更正）。
2. **哈希不许握着库锁**：`gfile_ledger_repair` 收的是 `Result<String, String>`（调用方在阻塞池里算好的那份），
   不是自己就地算。理由：本仓只有一个 tokio runtime，而 `state.db` 这把锁上排着消息收发与所有会读库的命令，
   GB 级哈希握着它几秒 = 那几秒整条链一起等。形状判据按"全册只这一处整文件哈希"钉住它不被搬回去。
3. **候选闸排在盘之前**：先三个走索引的点查（recipient / `is_transfer_done` / `content_transfers` 那一行），
   三张都收口的行**一次盘都不碰** ⇒ 健康机器跑这一趟的代价是一次 SELECT。
4. **recipient 行不在 ⇒ 不造它**（`update_group_file_recipient` 自己的规矩是"不静默创建群外 state"，
   权限归 Offer 那一段），另两格照写并留一条 warn —— 少一格不等于这台永远不算种子。

判据实测（本册现在共 **8 条 `#[test]`**，两平台基线各登记 8 条、双向差集为空）：

七条用例第一次跑的红不是产品缺陷：新写的 `gfile_ledger_repair` 又漏了一次 `tx.commit()`，被正向用例当场报「recipient 仍是 sending」。
接线那条也第一次跑就红，**红在判据自己** —— 我照搬 INV-P34 那句「交出点与慢活之间不许 `.await`」，而这一格在 spawn 之后先 sleep 20 秒，那个 `.await` 是刻意排在调用前面的；改的是判据（认 `spawn(async move {` 这个整体形状），不是把 sleep 挪走。

⚠️ 本册这一节随后又被两路只读审查推着改了三次（评审详见 `docs/archive/audit/ledger-2026-10-16.md` §5 第 14~18 行）：① 完成标记原来**无条件写** ⇒ 加 `incomplete` 门（一次 SQLITE_BUSY 不该把这台永久钉成不再补账）；② 接线那条用例原本落在 `mod` 外面 ⇒ 没有 `#[cfg(test)]`、会被编进 release；③ 候选扫描原来在 async worker 上握着全局 db 锁做全索引扫 ⇒ 整段进 `spawn_blocking`。最终整册现读 **880 通过 / 0 失败**，`fmt`/`clippy -D warnings`/`verify-guards --list`/快速层 17 步/测试清单守卫各退 0。

仍然没验的（如实登记）：

- 这一趟**没在真机上跑过**：本机没有那批缺账的库（`2de9264` 之后我本机没走过群接收收尾），
  所以"存量确实被补上"只有单测判据，没有装机读数。等 Windows 那一轮抓崩溃日志时顺带现算一次：
  `SELECT COUNT(*) FROM content_transfers WHERE direction='receive' AND path IS NULL` 与
  `群文件台账补账跑完：候选 N、补上 N、跳过 N、对不回身份的卡片 N` 那条日志。
- `list_gfile_ledger_gaps` 的**规模**没量过：它按 `msg_id LIKE 'gfile-%'` 全量扫卡片行，
  每条三次点查。重度用户的机器上这是启动后 20 秒的一次 SELECT，握库锁的时长 = 行数 × 三次点查，
  今天没有读数 ⇒ 如果将来日志里"跑完"那条迟迟不来，先量这一格，别先怀疑哈希。
