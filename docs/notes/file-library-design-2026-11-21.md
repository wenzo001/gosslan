# 统一文件库（J3-6）设计稿：微信式的文件处理，我们自己的交互

> 2026-11-21。口径来自用户拍板：「**按照微信的方式存储文件、处理文件、保存文件，但交互还是按照我们的交互**」。
> 本文只给方案与待决项，不预设结论；`file:line` 是本次快照，判现状以代码为准。

## 0. 一句话

把「收到的文件」从**用户下载目录里的散落文件**，升级为**应用自己管得住的一等资产**：
本地有一份就随时能打开（离线也行），本地没了就明确标"已清理"并支持按需重拉。
聚合成一个文件库视图，交互走我们已有的列表/筛选/详情范式。

## 1. 现状（事实）

| 事实 | 证据 |
|---|---|
| 收到的文件落在**用户选的接收目录**，该目录可改、会被保留期与配额清理 | `src-tauri/src/user_dirs.rs:33`（`RECEIVE` = `downloads_dir`）、`src-tauri/src/storage/cache_cleaner.rs:3-7` |
| 本机发出的媒体落在**托管的 sent 目录**（不进接收目录，避免被保留期删） | `src-tauri/src/commands/files.rs:95`、`:165` |
| 群文件已有完整的面板数据源：DB 行 + 每文件磁盘 stat + 送达汇总 | `src-tauri/src/commands/files.rs:434`（`list_group_files`）、`src/components/GroupFilesPanel.vue:11` |
| 「本地这份还在不在」已有批量探测命令，零新后端 | `src/api/index.ts:647`（`files_present`） |
| 收藏是**用户主动收藏**的消息/文件，与「所有收发的文件」不是一回事 | `src/components/FavoritePanel.vue`、`src-tauri/src/commands/favorites.rs` |
| 主导航只有四格：聊天 / 通讯录 / 收藏 / 设置 | `src/i18n/locales/zh-cn.ts:27-30` |

**结论**：缺的不是"下载"，是**聚合视图 + 可用性状态 + 统一的打开/另存语义**。
`files_present` 与 `list_group_files` 已经把最难的两块（磁盘探测、按会话取文件）做完了。

## 2. 微信到底怎么"存、处理、保存"（逐条对照）

微信 PC 的行为可以拆成四条，逐条判断我们该不该照做：

| 微信行为 | 本质 | 我们照做吗 | 理由 |
|---|---|---|---|
| 文件进**应用私有目录**，用户不知道在哪 | 应用是文件的保管者 | **照做，但分两步** | 先做索引层（不动落点），再评估"托管目录"。一步到位会让老用户已下载的文件"消失" |
| **不按保留期静默删除**文件 | 用户资产默认永久 | **照做** | 我们现在的 `retention_days` 会删接收文件；文件库里的条目必须**豁免**保留期，或至少清理前明确告知 |
| 本地没了 → 从服务器按需重拉 | 文件是"随时可取"的 | **照做（我们是对端）** | 我们已有 `request_content` / `request_content_by_cid`，缺的是"从文件库这一行触发" |
| 「另存为」才导出到用户目录 | 导出是显式动作 | **照做** | 与现有"打开/在文件夹中显示"并存 |

**不照做**：微信的界面（会话内文件条、右侧文件面板的分栏）。我们用虚拟列表 + 类型筛选 + 来源标签。

## 3. 方案（推荐）

### 3.1 分两步，先低风险的一步

**第一步（本次建议做）：文件库 = 索引层 + 视图。不改任何落盘路径。**
- 数据源：`messages`（kind=file/image）+ `group_files` 统一查询，按时间倒序游标分页。
- 每一行带：文件名、大小、来源会话、发送/接收、时间、`present`（本地在不在）。
- 操作：打开 / 另存为 / 在文件夹中显示 / 转发 / 删除本地副本。
- 本地不在 ⇒ 行上写"已清理"，点开走 `request_content` 重拉（对端在线才有，UI 要说清）。

**第二步（评估后再做）：托管目录。** 新接收的文件落 `file_library/<yyyy-mm>/`，
接收目录只保留"用户另存"的副本。需要一次性迁移 + 让老文件仍能被索引到。

### 3.2 后端接口（第一步）

```
list_file_library(cursor?: string, limit?: u32, kind?: "all"|"image"|"doc"|"media", conv_id?: string)
  -> { items: FileLibEntry[], next_cursor: Option<String> }

FileLibEntry {
  msg_id, conv_id, conv_title, kind, name, size, ts,
  direction: "in"|"out", local_path: Option<String>, present: bool,
  transfer_state: "ok"|"cleaning"|"failed"|"unknown"
}
```

- 走 `spawn_blocking`（R-18 棘轮）；DB 取完**立即释放锁**，磁盘 stat 在锁外做（照抄 `list_group_files:441-465` 的既有纪律）。
- `present` 复用 `files_present` 的同一份实现，不写第二份判定。

### 3.3 交互（我们的范式）

- **入口**：主导航新增第五格「文件」，与「收藏」并列（推荐，理由见 §4）。
- 列表：`VirtualList` + `OverlayScroll`（与消息列表同源），时间分组标题（今天/昨天/更早）。
- 顶部一行筛选胶囊：全部 / 图片 / 文档 / 媒体；右侧一个"来源"下拉（全部会话 / 单个会话）。
- 行右侧留 hover 才显的操作条（打开、另存为、显示在文件夹、转发）；移动端改成点行开详情。
- 空态：一句话 + 「去聊天里发个文件」的 CTA（对齐 `ConversationList` 的空态口径）。
- 状态：`present=false` 的行整体降透明度，尾部一枚"已清理"胶囊，点击给出重拉入口。

## 4. 待你拍板的两个点（各给推荐）

| 点 | 选项 | 推荐 | 理由 |
|---|---|---|---|
| **入口层级** | ① 主导航第五格「文件」 ② 收藏里加分段 ③ 聊天窗侧栏 | **①** | 文件库是"跨会话"的全局视图，塞进收藏会与"主动收藏"语义打架（现在收藏是用户点星标的结果）；侧栏只服务单会话，覆盖不到 1:1 + 群 |
| **聚合范围** | ① 1:1 + 群文件统一列表（来源列标签） ② 分成两栏 | **①** | 用户找文件时记得的是"那个 PDF"，不是"它是群里的还是单聊的"；分栏会把同一件事拆成两处找 |

## 5. 不做的事（避免范围蔓延）

- 不做"文件夹/标签"这类文件管理器能力 —— 微信也没有，且与"找不到文件"的原始痛点无关。
- 不动 Frozen Core（消息表 schema 不变；文件库只读已有表 + 文件系统）。
- 不在第一步改落盘路径（迁移风险与"老用户文件消失"的代价不成比例）。

## 6. 验收口径（第一步）

1. 发一个文件给对端、对端收下 → 双方文件库各出现一行，`present=true`，能打开。
2. 手动删掉本地文件 → 刷新文件库 ⇒ 同一行 `present=false` + "已清理"胶囊，点开出现重拉入口。
3. 群文件与 1:1 文件出现在同一个列表里，来源标签正确、筛选"图片"只留图片。
4. 分页游标：滚到底加载下一页，不重不漏（同一秒多条时不出重复行）。
