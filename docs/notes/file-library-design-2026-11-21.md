# 文件怎么找（J3-6）决策记录：不建入口，就地右键定位

> 2026-11-21。两轮口径，**以后一条为准**：
> ① 上午：「按微信的方式存储文件、处理文件、保存文件，但交互还是按我们的交互」；
> ② 21:49 拍板：**「入口不需要加什么文件……没有什么聚合看的地方，就是单击右键，
> 聊天框群文件、单聊的文件，右键可以打开文件所在的文件夹，跟微信类似就行了」**。
>
> ⇒ 存档目的：把 ① 推导出的那套「文件库 + 聚合视图」**明确作废**，避免下次又按它去做。

## 0. 一句话

文件**该在哪就在哪**：收到的是接收目录里一个真文件、自己发的是原位置那个文件。
用户要的是「右键一下，在文件管理器里看见它」，不是再造一个应用内文件库。
`file:line` 为本次快照，判现状以代码为准。

## 1. 落地形态（已实现）

| 位置 | 入口 | 实现 |
|---|---|---|
| 单聊 / 群聊的文件消息气泡 | 右键 →「打开所在目录」 | `MessageContextMenu.vue`（`emit("reveal-file")`）→ `MessageItem.vue::revealFileFromMenu` → `useMessageFile.revealFile` |
| 群文件面板某一行 | 右键 →「打开所在目录」（**2026-11-01 就有**，N6-3） | `GroupFilesPanel.vue::revealInFolder` |
| 接收目录本身 | （既有）`open_downloads_dir` | `src-tauri/src/commands/share.rs:108` |

两条链最终都走**同一个出口** `utils/localFile.ts::revealLocalFile`：

- 桌面：`@tauri-apps/plugin-opener` 的 `revealItemInDir`。macOS 那一支是
  `NSWorkspace.activateFileViewerSelectingURLs`（**不 fork 子进程**，沙盒可用 ——
  与 `open_path.rs` 顶部记的 `/usr/bin/open` 那个坑同源）；Windows 是
  `SHOpenFolderAndSelectItems`（资源管理器里**选中**那个文件）。
- Android / iOS：没有"文件管理器定位"这件事（插件返回 `UnsupportedPlatform`）。
  统一返回 `"unsupported"` 并**不显示入口** —— 平台差异对用户无感（与
  `isWindows` 隐藏「复制文件」同一条口径）。

## 2. 三个必须一起满足的条件（缺一个就退回"点了没反应"）

1. **本地真有这份文件**才有入口：`useMessageFile.canRevealFile` = `fileMeta.path` 非空。
   传输中 / 已被存储清理时不显示（**不给灰项** —— 灰项比不显示更让人以为坏了，
   这是群文件面板在 N6-3 就定下的口径）。
2. **路径来源与「另存为」同一个**：`fileMeta.path` 经 `displayPathFor` 过滤
   （SEC-01：对端消息只认台账里的落盘位置，载荷里的 `path` 只有本机发出的才作数）。
   两处各取一份来源，就会出现"另存为能点、定位不能点"的岔口。
3. **动作只有一个家**：菜单只 `emit`，插件调用只在 `utils/localFile`。
   判据见 `src/utils/contextMenu.test.ts` 末尾那条（含正控：砍掉 `v-if` 必红）。

## 3. 被否掉的方案（存档，别再做一遍）

- ❌ 主导航第五格「文件」+ 跨会话聚合列表（图片/文档/媒体筛选、来源标签、已清理胶囊、
  按需重拉）。当时推荐它的理由是"用户找文件时记得的是那个 PDF，不是它在哪个会话"，
  但用户的原话是「没有什么聚合看的地方」——**找文件的动作发生在聊天里，不在一个总目录里**。
- ❌ 托管目录（新接收文件落 `file_library/<yyyy-mm>/`，接收目录只留另存副本）。
  用户明确「发文件和收文件和以前一样」⇒ 落盘路径**不动**。
- ❌ 收藏里加分段 / 聊天窗侧栏 —— 同上，都属于"再造一个入口"。

## 4. 仍然存在的事实（本次不处理，但别忘）

| 事实 | 证据 | 影响 |
|---|---|---|
| 接收文件落在用户选的**接收目录**，会被保留期与配额清理 | `src-tauri/src/user_dirs.rs:37`、`src-tauri/src/storage/cache_cleaner.rs` | 清理后该条消息的右键项会**消失**（`path` 没了）——这正是"不给灰项"的口径；用户要重取走既有的 `request_content` 重拉 |
| 群文件与单聊文件**不共享**同一份列表 | 群文件有 `list_group_files`，单聊只有消息行 | 现在不需要共享了（没有聚合视图） |
| 自己发出的文件不在接收目录，而在原位置 | `displayPathFor` 回退载荷 `path` | 「打开所在目录」定位到**原文件所在目录**，与微信"复制进自己的 FileStorage 再定位"不同 —— 但对用户是同一句"我的文件在哪" |

## 5. 验收口径

1. 单聊收到一个文件、传完 → 右键气泡「打开所在目录」⇒ 文件管理器打开接收目录并选中该文件。
2. 自己发的文件 → 右键 ⇒ 定位到**选择发送时那个位置**的目录。
3. 文件还在传（`path` 空）→ 菜单里**没有**这一项（不是灰的）。
4. 群文件面板某行右键 →「打开所在目录」⇒ 与 1 相同。
5. Android 长按文件气泡 → 面板里**没有**「打开所在目录」（只有保存/转发等）。
